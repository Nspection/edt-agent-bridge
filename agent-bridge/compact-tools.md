# Компактный MCP и выбор способа проверки

Обычный `tools/list` возвращает до десяти входов: `edt.status`, `edt.search`,
`edt.inspect`, `edt.edit`, `edt.diff`, `edt.check`, `edt.run`, `edt.debug`,
`edt.task`, `edt.help`. Группы без доступных операций не показываются.
Имена и аргументы прежних операций сохранены; они доступны напрямую.
`tools/list` с параметром `profile=legacy` возвращает прежние полные схемы.

## Поиск операции и вызов

1. `edt.help` с `args={"action":"operations","filter":"infobase","limit":20}`
   возвращает короткие описания, каноническое имя `op` и нужный вход `entry`.
   Следующие страницы: `offset`; максимальный `limit` — 50.
2. `edt.help` с `args={"action":"contract","op":"edt_infobase_bind"}`
   возвращает полную схему одной операции.
3. Вызвать указанный `entry` с `{"op":"edt_infobase_bind","args":{...}}`.
   Аргументы, validation token, ограничения доступа и результат обрабатываются
   прежним исполнителем. Компактный вход не даёт дополнительных прав.

`edt.status` без аргументов вызывает `edt_bridge_status`. Остальные группы без
`op` показывают свои операции. Явный запрет входа скрывает его; запреты исходных
операций продолжают действовать. Для старых клиентов остаются прежние команды.

В измеренном тестовом каталоге 156 полных схем занимали 199750 байт JSON,
десять компактных — 5456 байт (примерно на 97% меньше). Это размер объявления
инструментов, а не измерение расхода токенов всей задачи; раскрытие контрактов
и результаты операций требуют дополнительного контекста.

## Маршрут проверки

`edt.run` с `op=route` и `args={"project":"MyProject","intent":"ui",
"required_actions":["open","input","command"]}` возвращает план и `next_call`.

- `code`, `query`, `data`: Native host для исполнения и проверки данных.
- `ui`: прямой TestClient, если доступны поддерживаемый Python и нужные действия.
  Native host можно дополнительно использовать для подготовки/проверки данных
  в той же явно проверенной базе.
- `scenario`, неподдерживаемые действия UI или отсутствие Python: Vanessa.
- `previous_state=running|outcome_unknown`: сначала расследовать исходную
  операцию; переключение исполнителя и повтор изменения не предлагаются.

Прямой UI поддерживает `open`, `close`, `input`, `command`, `wait`, `table_read`,
`table_select`, `table_add`, `table_set`, `batch`. План не устанавливает Python,
не запускает клиентов/базу, не обновляет конфигурацию и не меняет доверие.
Он проверяет проект и привязку, при необходимости проверяет наличие Python и
возвращает следующий явный вызов. Управляемая Python-среда готовится существующим
`edt_test_client`; системный Python изменять не требуется.
При отсутствии привязки план ведёт к списку зарегистрированных баз.

## Привязка существующей зарегистрированной базы

`edt_infobase_bind` принимает UUID из EDT, а не произвольный путь:

1. `action=list` — найти регистрацию (фильтр имени, страницы).
2. `action=preview`, `project`, `base_uuid` — получить снимок и `preview_sha256`.
3. `action=apply`, те же аргументы и `expected_preview_sha256` — применить
   привязку; дождаться `edt_operation_status` по возвращённому `job_id`.

`set_primary=true` по умолчанию. Замена другой основной базы требует явного
`replace_primary=true`. База другого проекта автоматически не перепривязывается.
Изменение контекста проекта, основной базы или целевой регистрации между preview
и apply отклоняется. Пароли, версия платформы и существующая регистрация
сохраняются. Команда не создаёт/не запускает базу и не загружает конфигурацию.
После привязки отдельно проверить `edt_infobase_state` перед обновлением/запуском.
Для существующей файловой базы вне workspace/home используется её зарегистрированный
UUID; ограничения прежнего `connect_infobase` на пути не ослабляются.

Повтор завершённого apply возвращает сохранённую квитанцию, а не повторяет
изменение. Квитанция — историческое подтверждение; `live_state=false` требует
отдельного чтения актуального состояния. Частичный/неизвестный результат не
повторяется автоматически и требует проверки исходной операции.

## Изоляция тестовой EDT

У отдельной EDT должны быть собственные workspace, MCP-порт и состояние запуска.
Не подключать тестовую EDT к пользовательскому серверу отладки на 1552.
Прямой TestClient запускается с отдельным свободным TPort без сервера отладки.
Для сценариев, где нужна отладка, явно проверить параметры debug launch и
принадлежность слушателя до запуска; совпадение порта не исправлять остановкой
чужого процесса.
