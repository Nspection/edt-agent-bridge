# Пакет Vanessa через настройки и MCP

С 1.4.0.20261111zzzzzzzzvanessa1 плагин подготавливает три закреплённых официальных артефакта: Vanessa Automation Single1.2.043.47, VAExtension1.43 и client_mcp0.6.6. Источники — GitHub Releases Pr-Mex/vanessa-automation и 1c-neurofish/onec-client-mcp-devkit, связанный из официальной справки Vanessa. Проверяются SHA256 архивов/файлов и EPF. Пакеты скачиваются отдельно по запросу, не входят в p2 ZIP.

Настройки MCP → «Vanessa Automation» → «Подготовить пакет Vanessa» и агент используют общий backend:

```json
{"op":"edt_runner_profile","args":{"action":"package_status"}}
{"op":"edt_runner_profile","args":{"action":"prepare_package"}}
```

Проект этим двум действиям не нужен. prepare_package возвращает job_id/next_call. package_status.ready=true со scope=package_only/state=package_ready означает только наличие проверенных файлов. runtime_ready=false; configuration_updated/trust_changed/client_started=false. Ответ содержит отдельные vanessa, va_extension, client_mcp с path/sha256 и готовые vanessa_epf/expected_vanessa_sha256 для профиля.

У put можно опустить ОБА vanessa_epf и expected_vanessa_sha256. Прочие поля профиля — platform_bin, manager_infobase_path, params_template и точная файловая/серверная цель — по-прежнему нужны. Неполная пара и неверный профиль отклоняются до скачивания. Полная явная пара сохраняет выбранную пользователем обработку.

При автоматическом выборе артефакта вся операция получить пакет → сохранить профиль выполняется фоновым заданием. Сохранить job_id, наблюдать next_call, затем читать get того же project/profile_id. Одинаковые активные запросы возвращают исходное задание, отличающиеся отклоняются. Явный put также не обгоняет активную подготовку. Перед записью проверяется исходный хеш файла профиля: изменённый профиль сохраняется, исходное задание завершается ошибкой. После неизвестного исхода не повторять запись вслепую; сначала исходное задание и актуальный get.

Профиль остаётся configured_not_live_checked. Порядок дальнейшей подготовки:

- Отдельная база менеджера, отличная от целевой. В ней устанавливается client_mcp; его имя должно быть client_mcp.
- VAExtension устанавливается в разрешённую целевую базу для операций, которым она нужна. Скачивание CFE само не устанавливает расширение. client_mcp и VAExtension выполняют разные задачи.
- edt_runner_prepare проверяет/готовит точечное доверие выделенного менеджера по существующему preview/apply. edt_runner_extension проверяет флаги установленного client_mcp; эта команда его не устанавливает.
- Затем штатный запуск /TestManager и проверка каталога/личности целевого клиента. Наличие файлов или сохранённого профиля не заменяет живую готовность.

Официальная справка: https://pr-mex.github.io/vanessa-automation/dev/AI/. Особые требования более новых функций (например restart_vanessa с VAExtension1.44+) не считаются выполненными поставкой1.43. Поддержка каждой функции проверяется отдельно по живому каталогу и контракту.

Хранилище LOCALAPPDATA/EDT-Agent-Bridge/runtime/<workspace_hash> с отдельными каталогами vanessa/vanessa-extension/client-mcp. Совпадающие файлы повторно не скачиваются, изменённая generation сохраняется на месте; восстановление создаёт новую. Проверяются квоты, безопасные пути и полное совпадение с закреплённым источником. После четырёх generations нужна проверка старых файлов; широкого автоматического удаления нет. Сеть и проверка файлов выполняются вне UI. Python/Native не требуют Vanessa.

Приёмка этого этапа: получение трёх артефактов, SHA256, cold profile job/dedup, кеш после рестарта и запись/чтение профиля в собственной EDT. Пути баз в проверке профиля были placeholders. Менеджер, установка расширений и бизнес-сценарий в этом этапе не запускались; чужие EDT/базы не использовались.
