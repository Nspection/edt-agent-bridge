# Серверное восстановление DT и доступ EDT — проверка

В исходном сценарии этап `backup_existing` объединял отключение синхронизации и экспорт, поэтому ожидание окна EDT выглядело как работающая резервная копия. При отсутствии явного логина прежний код передавал аутентификацию ОС. Теперь сохранённый доступ читается штатным менеджером EDT для точной регистрации с UUID и нормализованным подключением. Проверенный старый доступ используется для создания резервной копии и входа перед импортом. Нативный запрос доступа может обновить аргументы во время выполнения.

Для управления диалогом проверяются тип SDK, UUID и подключение, родной поток SWT или фактический владелец текущего запроса Workbench, исходное задание, одноразовый идентификатор и MCP-сессия. Только нативный запрос того же задания можно отменить через Bridge или открыть для него защищённый ввод. Отмена подтверждается финальным результатом исходного задания. При подтверждённом ожидании чужого окна в общем пуле Designer прогресс сообщает об этом и предлагает ручное действие в EDT. Этот пассивный датчик действует во время наблюдаемых нативных вызовов. Отдельный предшествующий этап `disconnect_existing` может потребовать ручной разблокировки существующего окна EDT.

После подтверждения защищённого ввода Bridge продолжает то же задание. Повторяется только чтение бэкапа или проверочный экспорт, каждый раз с отдельным выходным путём, если необходимо. Импорт выполняется после проверенной копии. Неопределённый результат оставляет файловый маркер блокировки для той же базы. Подтверждённый импорт отмечается отдельно до проверки новых реквизитов. Первое FULL-обновление использует сохранённый доступ EDT. Для защищённого ввода сохранение требует отдельного флажка. При отказе от сохранения Bridge возвращает подтверждённый экспорт и признак требуемого FULL. Ручной ввод в нативном диалоге использует штатное сохранение EDT.

На собственной EDT 2026.1.2.2 и отдельном сервере 1С 8.3.27.2325 с PostgreSQL 11.5 проверено реальное изменение тестового администратора после загрузки DT. Точная сборка использовала уже сохранённый рабочий доступ, получила непустой бэкап перед единственным импортом и остановилась на `verify_restored_access`. Защищённый ввод нового доступа в EDT, явное сохранение и команда продолжения вернули `restore_verified=true` и нативный `EQUAL`. Компактный статус сохранял состояние запроса. Другая MCP-сессия получила отказ. В отдельном прогоне устаревший сохранённый доступ привёл к запросу на `backup_existing`. Отмена из исходной MCP-сессии закончилась `cancelled` без импорта. Случай неизвестного импорта и блокировка нового apply проверены моделью.

Проверка журналов MCP и EDT на стенде не обнаружила значений тестовых паролей. Bridge не передаёт защищённые реквизиты в MCP и отказывает при включённой трассировке команд SDK. Штатный launcher 1С использует реквизиты в аргументах локального процесса. Сканирование журналов относится к стенду и фактической конфигурации трассировки.

Временная файловая ИБ очищена по lease. Собственные EDT, кластер 1С и оба экземпляра PostgreSQL остановлены, тестовые порты закрыты. Данные серверных стендов и квитанции остались в локальных каталогах прогона. Пользовательские EDT, x5 и базы в приёмке не участвовали.
