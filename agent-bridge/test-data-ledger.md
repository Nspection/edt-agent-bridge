# Учёт, создание и безопасная уборка тестовых данных

Доступно с выпуска `1.4.0.20261108workflow6`. Проверочная сборка устанавливалась только в отдельную EDT Dev. Создание и пометка удаления проверены на собственной файловой базе 1С 8.3.27.2325 в отдельной EDT. Сценарии и границы проверки — [test-data-validation.md](test-data-validation.md).

## Журнал

`edt_test_data` хранит журнал вне Git в `.metadata/.plugins/com.codepilot1c.core/test-data`. Он связан с проектом и UUID текущего native-приложения EDT. Смена привязки/проекта блокирует прежний журнал. UUID приложения не доказывает неизменность состава базы после восстановления DT.

- `begin(project,idempotency_key,label)` возвращает data_run_id/revision. Повтор после перезапуска сохраняет тот же журнал; другая метка с тем же ключом отклоняется.
- `register(...,expected_revision,records)` регистрирует 1–100 ссылок Catalog.Name/Document.Name, до 1000 в журнале. Необязательны expected_version/source_request_id. Это ownership=reported_by_agent: существование, версия и происхождение записи не подтверждены. Нельзя вручную указать подтверждённое владение.
- `list` возвращает записи постранично (offset/limit 1–100), total/revision/has_more.
- Повторы точной записи не дублируются. Конфликт версии или устаревшая ревизия не перетирают данные и не записывают часть пакета.

## Создание через уже работающий native host

Нужны существующие метаданные и заранее подготовленный/подключённый host той же базы и проекта. Команда не запускает клиент, не создаёт базу, не устанавливает компоненту и не обновляет конфигурацию. Режим host external/metadata и его подготовка — отдельные операции с прежними границами разрешений.

```json
{"action":"create","project":"TestConfiguration","data_run_id":"<из begin>","expected_revision":0,"idempotency_key":"fixture-item-1","host_id":"<работающий native host>","metadata_fqn":"Catalog.TestItems","fields":{"Наименование":"Тестовый элемент"}}
```

Поддержаны обычный элемент справочника и запись документа с явным РежимЗаписиДокумента.Запись. Поля — строки, числа до поддерживаемой точности, булевы значения и даты вида {"type":"date","value":"20261108120000"}. Ссылки и табличные части пока не поддержаны. Системные поля ссылки, группы, предопределённых данных, проведения/удаления и служебные флаги загрузки задавать нельзя. Пользовательский код и UUID не принимаются.

Исполнитель заранее сохраняет UUID, одноразовый маркер и спецификацию. В базу передаётся фиксированный серверный рецепт: штатная исключительная блокировка по зарезервированной ссылке, проверка её отсутствия, стандартная фабрика 1С, заполнение значений параметрами, запись в транзакции, чтение версии и её проверка после фиксации. Значения не склеиваются с BSL-кодом. Вложенная чужая транзакция запрещена. Если режим базы не поддерживает используемую управляемую блокировку, операция должна завершиться отказом, а не записью без проверки конкуренции. Данные приложения не пишутся прямым SQL; привилегированный режим и отключение прикладных обработчиков не используются.

Ответ create содержит creation_id/request_id. Затем:

```json
{"action":"create_status","project":"TestConfiguration","data_run_id":"<журнал>","creation_id":"<создание>"}
```

Только state=completed и confirmed=true означают принятую квитанцию. Журнал проверяет native request ID, протокол, маркер, метаданные, UUID и снимок версии, затем атомарно сохраняет запись с ownership=native_host_confirmed. Это подтверждение непосредственного создания на момент операции, а не разрешение на последующее удаление и не гарантия неизменности всех значений реквизитов. Прикладные обработчики могут преобразовать значения и иметь другие побочные эффекты, которые автоматически в журнал не попадают.

## Сбои и повторы

Ключ создания привязан к журналу, host и спецификации. Повтор не создаёт новый объект; изменение аргументов с тем же ключом отклоняется. До native-отправки сохраняется намерение, до принятия квитанции владение не подтверждается. Потеря ответа при отправке, отсутствие результата, несовпадение квитанции или ошибка после возможной фиксации дают outcome_unknown без слепого повтора. UUID остаётся в статусе для проверки фактической базы. Не менять ключ или host ради обхода неизвестного исхода.

Явная квитанция отката даёт failed и не добавляет объект. Успех транспорта или execution.success сами по себе не подтверждают создание: ответ рецепта может сообщать об откате. Ожидающее/неизвестное создание блокирует ручное редактирование списка и закрытие журнала. Поля создания сохраняются в приватном рабочем журнале для восстановления; использовать тестовые значения, не учётные данные подключения.

## Безопасная уборка: только пометка удаления

`preview_cleanup` возвращает неизменяющий базу план с `plan_sha256`, охватывающим весь журнал, а не только страницу. Любая новая запись или операция делает прежний хеш устаревшим. Затем можно **явно** пометить один объект:

```json
{"action":"cleanup","project":"TestConfiguration","data_run_id":"<журнал>","idempotency_key":"cleanup-item-1","host_id":"<работающий host этой базы>","record_id":"<record_id из list>","expected_plan_sha256":"<хеш из свежего preview_cleanup>","cleanup_mode":"mark_deletion"}
```

Ответ содержит `cleanup_id` и `request_id`. Опрашивать:

```json
{"action":"cleanup_status","project":"TestConfiguration","data_run_id":"<журнал>","cleanup_id":"<из cleanup>"}
```

Уборка принимает только `ownership=native_host_confirmed` с сохранённой квитанцией создания. Произвольные UUID и ручные `register` права на уборку не дают. В транзакции берётся исключительная блокировка по ссылке, сверяется версия из квитанции. Изменённый, предопределённый, проведённый или уже помеченный объект пропускается без записи. У справочника каскадная пометка подчинённых **отключена**. Прикладные обработчики выполняются; они могут иметь собственные побочные эффекты. Отсутствие исходной транзакции, наличие пометки и версия дополнительно проверяются после фиксации.

- `state=completed, outcome=marked_for_deletion` — подтверждена пометка, запись ещё существует.
- `outcome=already_absent` — подтверждено наблюдение отсутствия; инструмент не заявляет, что он удалил запись.
- `state=skipped` с `version_changed|predefined|posted|already_marked` — ничего не изменено этой операцией.
- `state=failed, outcome=rolled_back` — рецепт вернул подтверждение отката своей транзакции. Это не гарантия отката внешних эффектов прикладных обработчиков.
- `outcome_unknown` — не повторять под другим ключом. Сначала проверить сохранённое native-задание и фактическую базу.

Намерение уборки сохраняется до отправки и выдаётся только один раз. Квитанция связана с request ID, одноразовым маркером, record ID, UUID и исходной версией. Для той же записи второе намерение не создаётся, даже под новым ключом. Повтор с прежним ключом читает статус сохранённой операции. Незавершённая/неизвестная уборка блокирует новые записи и закрытие журнала.

Физическое удаление, поиск и очистка ссылок, отмена проведения, привилегированный режим и принудительное удаление изменённых объектов **не реализованы**. `physical_delete_performed=false`, `database_cleanup_verified=false`; `data_may_remain=true` для журналов с записями. Помеченные записи требуют обычной процедуры удаления приложения с контролем ссылок либо удаления целиком собственной одноразовой базы. Не применять старый журнал после восстановления DT: UUID приложения EDT не является идентификатором эпохи данных базы.

`close` с актуальным хешем закрывает только журнал, сохраняя квитанции. Он не удаляет записи, базы, host или проекты. Уборка host и отмена Vanessa также не откатывают деловые данные.

## Проверки и ограничения

Локальная сборка `1.4.0.20261108testdata7`: 497 Java-тестов прошли, границы standalone-пакета проверены. Реальная проверка: создание справочника/документа, дата и режим без проведения, повтор без дубля, откат при неверном поле, пометка удаления обоих типов, пропуск изменённой записи, отказ неподтверждённой ссылке и независимое чтение результата из базы. Окончательная сборка повторно прошла создание/пометку обоих типов. Проверки `predefined/posted/already_absent`, подмены квитанции и потери ответа выполнены управляемым Java-backend; отдельная живая приёмка этих веток не заявлена.

Серверный кластер, платформа 8.5 и прикладные обработчики x5 этой проверкой не охвачены. В пользовательскую EDT пакет не устанавливался; публикации не выполнялись.

## Именованные связанные наборы

Набор содержит 1–20 элементов справочников или документов. Значение `{"ref":"Alias"}` ссылается только на другой объект **того же набора**. Неизвестные имена и циклы отклоняются до первой записи; порядок вычисляется по зависимостям. Ссылки получаются из подтверждённых квитанций журнала. Перед записью зависимого объекта серверный рецепт проверяет существование, отсутствие пометки и исходную версию связанных записей под разделяемой блокировкой.

```json
{"action":"create_set","project":"TestConfiguration","data_run_id":"data-...","host_id":"...","idempotency_key":"fixture-chain-1","auto_advance":false,"items":[{"alias":"Partner","metadata_fqn":"Catalog.Partners","fields":{"Наименование":"Тестовый партнёр"}},{"alias":"Order","metadata_fqn":"Document.Order","fields":{"Partner":{"ref":"Partner"},"Дата":{"type":"date","value":"20261108120000"}}}]}
```

`auto_advance=false` — значение по умолчанию. Подготовка сохраняет план, но не создаёт данные. Для одного следующего шага:

```json
{"action":"advance_set","project":"TestConfiguration","data_run_id":"data-...","set_id":"set-..."}
```

Затем `set_status` с теми же project/data_run_id/set_id опрашивает текущее задание и возвращает подтверждённые `aliases`, `created_count`, `next_alias`, `creation_id/request_id`. В ручном режиме повтор статуса **не начинает следующий объект**. Самостоятельные `create/create_status`, native BSL, Vanessa и остальные команды остаются доступны; новые наборы не являются обязательным путём.

При явном `auto_advance=true` первый шаг запускается при создании набора; последующие `set_status` могут отправлять следующий шаг. Это сохранённый автомат, а не скрытый бесконечный worker: одна отправка за вызов. `pause_set` с set_id останавливает **будущие** автоматические отправки; уже отправленное задание не отменяется. В паузе можно читать `set_status` и отдельно выполнять `advance_set`. `resume_set` возвращает возможность автоматического продолжения при следующих запросах статуса.

Каждый объект записывается собственной транзакцией. Набор не атомарен целиком: частичный успех остаётся в `aliases`. При failed/outcome_unknown зависимые объекты не запускаются. Не заменять ключ для обхода неизвестного исхода; доступны идентификаторы отдельных операций. Изменённый план с прежним ключом отклоняется. План, ключи шагов и подтверждённые записи сохраняются вне Git; перезапуск не дублирует подтверждённые узлы.

Для уборки набора сначала `preview_set_cleanup`, затем `cleanup_set` с `expected_plan_sha256` из preview и явным `cleanup_mode=mark_deletion`. Порядок обратный: документ → дочерний объект → родитель. В ручном режиме продолжать через `advance_set`; в автоматическом — через `set_status`. Если дочерний объект сохранён из-за изменения/отказа, его предки получают `dependent_retained` и тоже сохраняются. `completed_with_skips` означает, что часть записей осталась. Неизвестный исход блокирует дальнейшие записи/закрытие журнала до разбора.

Наборы не добавляют физическое удаление, проведение, табличные части, произвольные ссылки на чужие данные или циклические зависимости. Уборка — только защищённая пометка удаления. Прикладные обработчики могут преобразовывать значения и иметь неучтённые внешние эффекты. Для нестандартных задач агент может пользоваться исходными пошаговыми командами и разрешённым native BSL.

Живая проверка: три связанных объекта справочник → справочник → документ; независимое чтение обеих ссылок; ручной и автоматический режимы; пауза, одиночный шаг и resume; обратная пометка; сохранение изменённого дочернего объекта и его родителя; отклонение циклического плана. 510 Java-регрессий и границы standalone-пакета прошли. Проверка выполнена на собственной файловой базе 8.3.27.2325, не на кластере/8.5 или бизнес-обработчиках x5. Локальные доказательства: `.runs/changes-sets/state.json`, `tests6.log`, `cleanup.json`.

Исправления ревью workflow6: HTTP MCP, структурированные ответы и native host сохраняют точность чисел через BigDecimal. Журнал набора восстанавливает подтверждённый одиночный шаг при потерянном ответе и подхватывает уборку, выполненную отдельной primitive-командой, без повторной записи. Итог уборки сверяется с авторитетным журналом, а не только с кэшем набора. После отката BSL дополнительно проверяет фактическое состояние непосредственного объекта; если обработчик уже зафиксировал изменение, возвращается ошибка/неизвестный исход, а не ложная квитанция отката.
