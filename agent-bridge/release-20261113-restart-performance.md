# EDT Agent Bridge 1.4.0.20261113restart1

Исправлены подтверждённые причины лишней нагрузки при повторной работе с EDT и зависание недоставленных Native-запросов. Пользовательские EDT и базы не изменялись.

- Завершённые TestClient receipts хранятся отдельно в history. Старые cleaned-каталоги переносятся только при подтверждённом ID и единственном client.json, без перезаписи существующей истории. Изменённые/неизвестные файлы сохраняются. Статус stopped/cleaned больше не разрешает приложение и не хеширует EXE клиента; закрытие не обрабатывает всю архивную историю как активные сессии. Архив только читается, повторная очистка его не меняет.
- Выбор маршрута и подготовительный этап читают только кандидат Python-окружения: candidate/ready=false/verification_required=true. Один полный inventory/SHA256/probe остаётся в select под блокировкой непосредственно перед запуском. Изменённое окружение по-прежнему блокируется, глобального кеша доверия нет.
- Периодический SWT callback привязан к поколению; stop отменяет именно свой callback, а поздняя отмена/старый callback не задевают новый запуск. Это исправляет дублирование при перезапуске плагина в той же JVM; процессы новой EDT не наследуют старые таймеры.
- Native проверяет принадлежащий хосту живой Process, PID и время запуска, а также свежесть успешного контакта. После hello стартовые диалоги окончательно закрыты для этой сессии, даже при потере heartbeat. Отсутствующий/неподтверждённый процесс запрещает новые операции.
- Native queued ограничен 60 секундами до доставки. poll, result/status и wait проверяют deadline под тем же lock, что durable delivered; поздний poll не исполняет отменённый запрос. При доказанном выходе своего клиента queued отменяется, delivered становится outcome_unknown с сохранением прогресса. Один stale heartbeat не отменяет уже исполняющийся BSL. Причина и not_dispatched видны в compact-ответе, исходный request_id/key сохраняются, автоматического повтора нет.

Проверки: 1256 Java и 179 Python тестов, 33 controller +3 CLI +13 startup PowerShell проверок, OSGi/boundary/provenance и p2 verifyOnly на копии профиля. Регрессии охватывают историю 100 очищенных клиентов, сохранение посторонних файлов, порядок блокировок, 1000 перезапусков таймера, конечную проверку Python после tamper, реальные HTTP hello/poll/result с управляемыми часами, queued expiry, длинный delivered, выход клиента, отказ записи и compact-квитанции. Проведены собственное и независимое Astra medium ревью.

Живая приёмка ограничена серией запусков/выходов собственной EDT без запуска ИБ, MCP-маршрутизацией и чтением очищенного клиента. Измерения приведены в сопровождающем ревью. Новые Native liveness/deadline ветви проверены детерминированным HTTP-протоколом, не новым клиентским прогоном 1С. Причина прежнего длительного зависания до перезагрузки ПК не считается установленной только этими исправлениями; короткая серия не заменяет длительный soak-test. Историческая классификация удаления Касперским остаётся неизвестной, исключения защиты не менялись.
