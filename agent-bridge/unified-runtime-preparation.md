# Единая подготовка runtime

Доступна с `1.4.0.20261110zzzzzzunified1`. Требует установленный edt_runtime_prepare; старые команды сохранены.
Компактный контракт: edt.help args={action:"contract",op:"prepare"}.

Пример вызова через edt.run:

```json
{"op":"prepare","args":{"action":"prepare","project":"MyTestProject","base_uuid":"UUID_FROM_EDT","intent":"ui","required_actions":["open","input","command","wait"],"idempotency_key":"task-ui-01"}}
```

Сохранить preparation_id и job_id. Дождаться edt_operation_status либо читать
edt.run op=prepare с args={action:"status",preparation_id:"..."}. Progress job
показывает этап; ready=true подтверждается свежей проверкой runtime и привязки.
Job DONE без ready=true не означает готовность и не подтверждает бизнес-тест.

Подготовка проверяет project/current branch context, точный UUID/target и native
EQUAL. При несвежем равенстве один раз выполняет штатный refresh с отложенными
конфликтами, без обновления/импорта конфигурации. NOT_EQUAL останавливает подготовку.
Она не привязывает базу, не обновляет конфигурацию и не меняет доверие.

- Код/запросы/данные: Native. Совместимый ZIP автоматически получается и проверяется
  общим сервисом; явная пара native_path/expected_native_sha256 остаётся доступной. Создаётся только внешний host и собственный клиент. Для
  metadata host с FULL-обновлением использовать прежний edt_runtime_host отдельно.
  Окно доверия оставляет исходный host в awaiting_runtime; status только наблюдает,
  не запускает замену. После штатного доверия можно читать этот же status.
- Поддерживаемый UI при наличии Python: TestClient. Плагин готовит/переиспользует
  собственный venv с pinned/hash-verified пакетами и запускает свой клиент.
  Системный Python не меняется. Результат содержит runtime.client_id для
  edt_form_state/edt_form_action с transport=testclient.
- Сценарий/неподдерживаемый UI/нет Python: Vanessa. Проверяются сохранённый
  profile_id, его целевая база, каталог менеджера и живой TestClient. Готовый
  менеджер заимствуется. Отсутствующие профиль/менеджер/доверие/расширения требуют
  отдельной штатной подготовки, возвращается блокер. Автоматической установки
  расширений, доверия или запуска нового менеджера здесь нет.

ID клиента/host записываются ДО запуска, Python — до создания venv. Повтор
ключа возвращает первоначальную подготовку, изменённые аргументы отклоняются.
Новый ключ не обходит незавершённый/неизвестный запуск в этом проекте. Готовый
клиент не дублируется другим ключом; отдельный Native-помощник допустим рядом
с заведомо готовым UI-клиентом. После рестарта незавершённая подготовка не
воспроизводится. Закрытый/потерявший привязку runtime не объявляется готовым
по историческому receipt. При known blocker до любых ресурсов допустим новый
исправленный запрос, но неизвестный исход требует разбора/уборки оригинала.

Уборка через edt.run op=prepare:

1. args={action:"cleanup_preview",preparation_id:"..."} — получить plan_sha256.
2. args={action:"cleanup",preparation_id:"...",expected_plan_sha256:"..."}.
3. Дождаться job и проверить state=cleaned и cleanup_state ресурсов.

Клиент/host убираются перед созданной Python-средой. Borrowed Python/Vanessa не
удаляются/не останавливаются. Изменённые/используемые ресурсы сохраняются;
частичная уборка требует нового preview тех же ресурсов. Базовый проект и база
не входят в эту уборку. Исходные команды доступны отдельно для расследования.

Подготовка — инфраструктура. Она не отправляет бизнес-действия и не подтверждает
успех будущего теста. Сначала ready, затем действия с собственными postconditions.

## Окно TestClient после подключения протокола

Старт наблюдает тот же процесс до 90 секунд после
соединения протокола; readiness_timeout_s допускает 10..180. Повторяются только
известные read-only condition_timeout, транспортная неопределённость прекращает
ожидание. Другой процесс или исполнитель автоматически не запускается.
client_kind=thin сохраняет прежний выбор; client_kind=thick явно выбирает
SDK-толстый клиент с RunModeManagedApplication. Оба параметра доступны также в
отдельном edt_test_client start. Они доступны с релиза unified1; compact1 их не содержит.

status сохраняет client_kind, startup_phase, protocol_connected и
startup_diagnostics даже после остановки неудачного старта. Timeout остаётся
retry_safe=false: отсутствие отправленных UI-команд не доказывает отсутствие
прикладных действий инициализации. Успех протокола не равен наличию окна.
Начиная с thinfix1 (включено в unified1) исправлен вложенный лимит: startup ready получает весь
оставшийся бюджет, включая wire receive и stdio reply, вместо обрыва одного
ответа через10с при общем ожидании90с. Обычные наблюдения сохраняют лимит10с,
действия — прежние пределы. Незавершённый ответ/EOF не пересылается и не
объявляется condition_timeout; диагностируется тип транспортной ошибки.
На TMS_FILE85 выполнены повторные штатные thin-запуски с чтением интерфейса;
подробности и границы доказательства — tms-testclient-install-validation.md.

## Project audit25: зависимости и единый startup budget

TestClient передаёт один оставшийся readiness budget через listener, handshake и UI; Python/connect/ready receive и stdio reply согласованы с этим пределом. Истёкший бюджет не отправляет новый ready RPC. Неизвестный wire outcome не повторяется.

Для managed Vanessa при отсутствии установленного PowerShell7: `edt.run op=edt_runner_profile args={action:powershell_status}`, затем `prepare_powershell` и опрос исходного job_id. Пакет Microsoft7.6.9 win-x64 закреплён SHA256, распаковывается в личный cache плагина и не требует системной установки. `edt_runner_prepare` возвращает needs_powershell с next_call; успешная подготовка интерпретатора не подтверждает готовность ИБ/Vanessa/расширений или доверие.
