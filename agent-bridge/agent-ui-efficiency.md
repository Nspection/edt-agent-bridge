# Короткий цикл агента: UI, подготовка и метрики

Доступно с `1.4.0.20261111zzzzzflow1`. Проверяйте `wait`/`details` в установленном контракте: в прежних релизах остаётся путь `edt_operation_status` → status. Число компактных входов не увеличено.

## UI-прогон

Один раз получить контракт `edt.help` для `op=ui`, затем вызвать существующий `edt.run` с `op=ui`, `args.action=start` и проверенным планом. В ответе есть `ui_run_id`, `next_call` и `details_call`. Например:

```json
{"tool":"edt.run","arguments":{"op":"ui","args":{"action":"wait","ui_run_id":"ui-…","timeout_ms":20000}}}
```

Вызывать этот объект напрямую, сохраняя исходный ID. Пока `terminal=false`, использовать следующий полученный `next_call`. Не повторять start для опроса. Отдельно читать job, а потом снова UI status больше не требуется.

`wait`: timeout_ms 0..25000, по умолчанию 20000. Ожидание job использует уведомление существующего registry; journal lock на время ожидания освобождён. Для ещё подключающегося Native предусмотрено ограниченное наблюдение без повторного запуска. Таймаут возвращает `timed_out=true` и текущий исход, не отменяет работу и не доказывает успех. Тайминги самой формы/операции (operation_timeout_s/wait_timeout_ms) не меняются: медленная форма может потребовать несколько wait.

start/status/wait возвращают компактный результат с ID клиента/подготовки/сессии, итогом теста и отдельным итогом уборки, счётчиками шагов, причиной/этапом отказа и артефактами. Полные значения, журналы и тайминги остаются в action=details по тому же ID. Обрезка не превращает failed/outcome_unknown в успех.

- У выполняющегося прогона next_call — wait исходного прогона.
- У failed/outcome_unknown — details исходной операции, без нового start/смены исполнителя.
- У успешного сохранённого клиента нет автоматического выбора между reuse и cleanup: следующее бизнес-действие задаёт задача.
- При незавершённой уборке успешного прогона предлагается только cleanup_preview. Применение по свежему hash остаётся отдельной командой.
- После явного cleanup возвращается готовый read-only next_call к edt.task/edt_operation_status для точного job, compact=true.

## Подготовка

У существующего op=prepare добавлены action=wait и details. prepare/status/wait по умолчанию краткие; details возвращает прежний полный публичный status со свежей проверкой runtime/binding. Внутренний request и произвольные лог-пакеты не раскрываются. UI Backend продолжает использовать прежний service status без сокращения данных.

Ready не выводится из сохранённой квитанции. После cleanup/binding failure старый вложенный runtime.ready не попадает в краткую сводку. Состояния blocked/needs_update/unknown ведут к details, не к новому prepare или обновлению базы. Доступы wait/details соответствуют прежнему status; ожидание не расширяет полномочия.

## Замеры

Существующий `edt_agent_metrics` без аргументов по-прежнему возвращает полный process snapshot с UI lag. Для малого ответа:

1. action=baseline — получить baseline_id без всех строк инструментов.
2. Выполнить выбранный сценарий.
3. action=changes с baseline_id — получить только изменившиеся счётчики.

Это операции существующего компактного входа edt.status; точный op — edt_agent_metrics. Baseline неизменяемый: повтор changes сравнивает с той же точкой, а не с последним чтением. Хранится до 1 часа, максимум16 на процесс; после рестарта/вытеснения нужен новый baseline. Неизвестный baseline не выдаёт выдуманные нули. Deltas включают собственные вызовы метрик/discovery; текущий запрос учитывается после ответа.

Компактные ui/prepare считаются под каноническими edt_ui_run/edt_runtime_prepare, а не unresolved. Отдельно видны edt.help.contract/operations/catalog; произвольные op или payload не сохраняются в именах. Байты — UTF-8 JSON-счётчики, не фактические токены/стоимость модели. Суммарная duration инструментов не равна времени сценария при параллельных вызовах.
