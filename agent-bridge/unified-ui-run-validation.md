# Приёмка единого UI-прогона и управляемых таймингов

10.11.2026. Ветка codex/unified-ui-run, кандидат1.4.0.20261110uirundev12.
Изменения локальные, без коммита/push/merge/release. Пользовательская EDT и базы
не запускались, не обновлялись и не перезапускались. Использованы отдельная
EDT Agent Bridge Dev, MCP8769, 1С8.5.1.1522 Windows x64 и три одноразовые
синтетические конфигурации/файловые базы. Это не приёмка ЦО/карты/Секций TMS.

## Поведение

- edt.run op=ui → edt_ui_run: полная проверка1..16 шагов до подготовки,
  явный UUID/EQUAL, существующие RuntimePreparationService и TaskSessionService
  с direct-адаптером, начальный snapshot, один журналированный batch, отчёт,
  PrintWindow только своего PID, уборка own/borrowed ресурсов.
- Сохранённый подробный результат читается после удаления клиента через
  edt_ui_run details. Summary ссылается на этот сохранённый отчёт.
- На конечном кандидате803 Java-теста и41 worker+16 table контрактов прошли;
  standalone boundary и p2 verifyOnly на скопированном профиле/собственном
  destination прошли. Одна более ранняя полная проверка встретила Windows
  file-lock в прежнем cleanup fixture; повтор и итоговый набор прошли,
  посторонний тест/реализация не менялись для обхода.

## Живые прогоны

Наv4/v8/v9 и конечномv12 пройден пакет9 шагов: открыть список, создать,
заполнить, сохранить, повторно открыть, сверить точное значение и закрыть.
Все9 postconditions подтверждены. Полный результат, повтор того же ключа без
новых запусков и снимки проверены; снимок собственного UiRunFixture просмотрен.
На конечномv12 задан operation_timeout_s90 и wait_timeout_ms60000 в открытии;
бюджет виден в timing_config, готовые формы возвращались сразу. Клиент и
созданная Python-среда убраны автоматически, session_closed=true.

Наv8 дополнительно: (1) несуществующее поле остановило пакет на шаге2,
шаг3 не выполнялся; (2) принудительное завершение своего1cv8c во время чтения
дало ConnectionResetError/failed без ложного успеха; (3) завершение собственного
worker по проверенным PID/start/image дало outcome_unknown, полный результат
сохранён, клиент убран, новый ключ отказал в обходе. Известный отказ чтения
не был ошибочно объявлен неизвестной мутацией. В диагностике ошибки шага
сохранён failed_stage и тип причины, не только job DONE.

## Медленные формы и бюджет

Переданный из другого чата postcondition TimeoutError разбирался по сохранённой
диагностике, без доступа к пользовательской базе. Найден самостоятельный дефект:
полл-таймаут мог обрывать незавершённый ответ посередине. Контрольный socketpair
с ответом через2с и ожиданием1с: публичный unified1 worker оборвал канал через
1001мс с TimeoutError; исправленный дочитал ответ за2000мс и сохранил канал.
Реальный транспортный timeout/EOF по-прежнему закрывает канал без повторов.

С явным operation_timeout_s90/wait_timeout_ms45000 настоящий задержанный ответ
socketpair принят через31000мс, канал цел, receive10с восстановлен. Это
контроль времени транспорта, не имитация фактической отрисовки карты в1С.

Параметры: operation_timeout_s5..300 (default25), wait_timeout_ms0..300000
в пределах бюджета операции; один бюджет на весь batch. Для UI-run он также
передаётся первоначальному чтению формы. IPC и долгий MCP form-state wait
согласованы с ним. Startup readiness отдельно10..180 (default90). Невалидные
бюджеты/поздние шаги отклоняются до мутаций, смена таймингов не обходит ключ.
Готовый результат возвращается сразу; ожидается явный признак формы/карты,
таймаут не равен обязательному sleep и не доказывает загрузку карты.

## Диагностика и границы

Измерены очередь, binding, Python, процесс, протокол, UI, пакет, capture и cleanup.
На холодной средеv8 подготовка32,8с, из них Python22,5с; само окно после протокола
готово примерно за1с. В конечномv12 подготовка35,0с, Python26,1с. slowest_stage
показывает preparing_python. Значительная часть тёплого времени также приходится
на повторную проверку Python; оптимизация проверок не подменяется новым таймаутом.
Статус показывает активную фазу, порог slow10с диагностический, не ошибка.
Нет командной строки/пароля/сырых пакетов в диагностике. Group/Page не выдается
за кнопку; direct/Vanessa опции разделены в schema и ошибках.

Объём JSON в финальном случае: status 5642байт, details 11398байт (примерно на50.5% меньше).
Это байты ответа одного примера, не расход токенов всей задачи. Каталог
сохранил10 компактных входов. Batch не транзакция, данные не откатываются;
бизнес-записи не удаляются runtime-cleanup. Долгий/неподдерживаемый UI по-прежнему
может требовать пошаговый путь или Vanessa. Не заявляется произвольная карта,
серверная база, другая версия платформы или исчезновение всех прошлых сбоев.
