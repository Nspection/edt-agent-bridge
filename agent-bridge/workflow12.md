# Изоляция host, отзывчивость и пакеты 1С: workflow12

Версия: `1.4.0.20261109zzworkflow12fix1`. Проверять схемы установленного MCP. Изменения не дают разрешения на обновление произвольной базы.

## Внутренняя обработка

Новый `edt_runtime_host prepare mode=metadata` создаёт только внутренний DataProcessor, форму и макет Native API ZIP. Внешнего проекта/EPF нет. `start` использует штатную навигационную ссылку `e1cib/app/Обработка.<имя>` через SDK runtime/access. Первый start выполняет FULL всего проекта; повторный start того же неизменённого ранее загруженного host при native EQUAL пропускает обновление. Защита подключения бинарной компоненты по-прежнему принадлежит платформе.

Cleanup проверяет владение/хеши, удаляет объект native-средствами, обновляет базу и независимо проверяет отсутствие через согласованный CF/XML-снимок и read-only Designer CompareCfg File против DBConfiguration. Поколение до/после экспорта должно совпадать. Неизвестный формат отчёта, различия и оставшийся объект блокируют успех. Успех: cleaned/source_removed/database_verified_absent=true. Legacy-host сохраняет совместимость; external-mode по-прежнему создаёт EPF.

## Пакет на стороне 1С

Один `execute` ставит до 16 явных клиентских/серверных шагов:

```json
{"action":"execute","host_id":"HOST","idempotency_key":"scenario-01","execution_mode":"batch","steps":[{"caption":"Открыть","context":"client","code":"Результат = 1;","screenshot":true},{"caption":"Проверить","context":"server","code":"Результат = 42;"}]}
```

Для реальной формы в code передаётся разрешённый BSL её открытия/изменения; пример выше проверяет транспорт. Каждый шаг получает собственные parameters как ПараметрыВызова и присваивает Результат. Лимиты: 8192 символа кода/шаг, caption 200, общий payload 128 KiB, результат 2 MiB. Следующий шаг выполняется на следующем тике 1С; снимок — на отдельном тике после отрисовки. Ошибка BSL завершает пакет с частичными результатами. Исключение вызова/разбора ответа серверного шага даёт terminal outcome_unknown, без повторного исполнения шага. Завершённый пакет фиксирует неизменяемый ответ до отправки Complete; при потере ACK повторяется только этот ответ до нового Poll. Нет транзакции на весь пакет и автоматического отката.

`result` возвращает массив результатов и описаний снимков. `snapshots` с host_id и необязательным request_id возвращает проверенные пути PNG/хеши/размеры без base64. Нужна компонента protocol2 с capability screenshot_png; старый ZIP отклоняется до запуска screenshot-пакета. Клиентский BSL также может вызвать `КомпонентаАгента.Screenshot()` и разобрать JSON через `HostReadJSON`.

Компонента снимает главное видимое окно только своего процесса. Лимиты и особенности PrintWindow описаны в [Native API README](../native/agent-host/README.md). Картинки хранятся до cleanup; нужные доказательства скопировать заранее. Остановка проверяется между шагами, не прерывает уже выполняющийся BSL и не откатывает записи. Выданный незавершённый пакет получает outcome_unknown; не повторять его новым ключом. Повтор прежнего ключа в том же host возвращает прежний request_id.

## Отзывчивость EDT

Тяжёлые задания infobase-* и native-host-* идут через отдельную последовательную очередь (до 16 ожидающих); лёгкие операции сохраняют пул из четырёх потоков. Фоновые потоки имеют низкий приоритет. Это уменьшает конкуренцию, но штатные операции модели/загрузки EDT всё ещё могут занимать UI.

`edt_agent_metrics.ui` содержит heartbeat, max_lag_ms, до 32 событий с UI-стеком (до 64 кадров) и именами активных операций. Один ожидающий heartbeat, период 250 мс, порог задержки 1500 мс. Аргументы/BSL/токены не записываются. Событие показывает совпадение во времени, а не само по себе причинность. Отчёт ui-lag.json хранится в state плагина.

## NOT_EQUAL после перезапуска

`edt_infobase_refresh {project}` штатно читает изменения и откладывает конфликты; не импортирует и не обновляет конфигурацию. NO_CHANGES не означает EQUAL. `compare_database=true` экспортирует CF/XML-снимок и read-only отчёт сравнения с конфигурацией БД; это не проверка равенства текущих исходников EDT.

Только явное `update_incremental=true` применяет ВСЕ текущие изменения проекта штатным инкрементальным обновлением разрешённой базы. При необходимости FULL команда отказывает; скрытого FULL нет. Флаги update_incremental и compare_database взаимоисключающие. Получить итог через edt_operation_status; сохранить job_id. Проверять фактическое equality, не подменять его NO_CHANGES или успешным транспортом.
