# Сравнение маршрута поиска и чтения контекста

26 прежних замороженных вопросов на отдельной копии TMS:5517 BSL,5806 mdo. Вопросы и положительные примеры подготовлены независимым ревьюером до BM25; SHA256 набора7dbeb9888588d3a8210885d9eba526165f54821049acd7985ceeaa12cef0b4a7 не менялся. Пользовательский код/вопросы приватны.

## Выбор поиска

Фактический lexical BM25 top5 против auto (6 identifier→literal cases,20 ranked cases): известный положительный метод в top5 **17/26 у обоих**. У20 вопросов выбранные наборы совпали, у6 literal route отличается. Для оценки literal hits offline mapper относит строку к методу; это только подсчёт релевантности, не бесплатное разрешение методов для агента. Не заявляются полнота, business correctness или успешное выполнение26задач LLM. Auto не заменяет явный text/regex и не ранжирует regex. Совместимость18 полных JSON-ответов проверена отдельно в OSGi.

## Пакетное чтение одинакового набора

Для каждого вопроса берётся фактический top5 BM25, из него выбираются уникальные методы. Оба маршрута читают ОДИН И ТОТ ЖЕ набор — без выбора по expected answers. Baseline: поиск+одиночные bsl_get_method_body; новый: тот же поиск+items с max_chars16000. Reader читает реальные сохранённые файлы копии, но это file-backed test provider, не BslSemanticService TMS. Настоящая semantic-приёмка выполнена отдельно на маленькой собственной конфигурации.

| Медиана по26 сценариям | Одиночные чтения | Batch |
|---|---:|---:|
| Логические вызовы поиска/чтения |6|2|
| Компактные JSON content bytes |20444.5|22151.5|
| Общая поисковая фаза + соответствующее file-backed чтение |1.164с|1.162с|

Это **уменьшение roundtrips**, не доказанная экономия токенов/денег и не ускорение SDK. JSON медиана выросла примерно8.3% из-за полей ошибок/усечения, исходных размеров и повторной идентификации элементов. Для8 методов в5 сценариях сработал общий лимит; это явно потеря середины excerpt, не сохранение полного текста бесплатно. Ошибок reader0 у обоих. Усечённые тела нельзя использовать как полные; singleton40000 и чтение точного диапазона остаются доступны.

Время использует одну и ту же измеренную поисковую фазу и отдельно измеренные этапы чтения; не является независимым latency-тестом двух MCP-клиентов. Холодный индекс56.504с вынесен отдельно. Java17/Xmx768m/ActiveProcessorCount=2, последовательный процесс ниже обычного приоритета; это условия одного запуска, не обещание времени на любой EDT.

Payload включает реальные поля content соответствующих serializers; search дополнен project/state/terminal/job_id, batch — state/job_id фиксированной длины. JSON-RPC envelope, pretty whitespace, транспортная обрезка и контекст/рассуждения LLM исключены. Warm logical calls не включают cold-index и slow-batch polls: их нужно отдельно учитывать при реальной работе по next_call. Auto literal→разрешение метода→чтение не объявляется маршрутом из двух вызовов.

Полный сценарий решения бизнес-задачи живым LLM и стоимость его токенов в этом этапе не измерены. Проверены retrieval-качество, orchestration, ограничения тела и совместимость; [контракт](search-context.md), [runtime и ревью](review-20261112-search-context.md).
