## Исправленные затраты и причины блокировок

Обычный compact-вызов больше не строит и не разбирает схемы всех N инструментов. Для выбора команды используются свежие названия, capabilities и policy; отдельный help contract загружает одну выбранную схему. Динамические exposure и авторизация проверяются при исполнении. Общий trust-cache не вводился. Тест считает обращения к schema providers: discovery и обычное выполнение не загружают схемы посторонних инструментов; один contract загружает одну; legacy tools/list сохраняет полные схемы.

Native execute использует одно свежее наблюдение совместимости вместо двух. execution_allowed и execution_blockers согласованы с отказами выполнения: state, текущая привязка базы, consent/startup, compatibility, refresh и cleanup. История исходного ключа проверяется до runtime-gates, поэтому остановка или отзыв согласия не превращает уже выполненную операцию в «не отправлено».

Сохранение живого Native receipt обращается к собственному claim по сохранённому пути. Прежний поиск разбирал до N полных JSON-файлов на каждый poll/progress/result. Проверка UUID/digest/ключа и факт исчезновения известного claim сохранены; повреждённый журнал не разрешает повтор или выдачу результата другого ключа.

Ожидание task batch освобождает monitor сессии между наблюдениями, сохраняет running до ожидания и перечитывает durable state после него. Конкурирующий observer не дублирует шаг и не перезаписывает уже продвинутый batch. Уже собранное batch-наблюдение остаётся исторической квитанцией; явная отдельная проверка формы остаётся доступной.

Прерванная распаковка зависимости больше не накапливает неактивированные runtime directories до исчерпания квоты. Старое асинхронное задание после stop/start не может активировать пакет или записать профиль. Большое число очищенных исторических runtime-каталогов не блокирует обслуживание другого проекта.

## Что ещё измерять

Проверка целостности portable PowerShell остаётся дорогой: для сохранённого архива109620855байт, сжатых payload109520901байт и распакованных файлов256666658байт один warm status логически читает около475.8МБ. Это расчёт объёма по реальному ZIP, не измерение физических дисковых чтений или секунд; файловый кеш ОС влияет на время. Этот путь относится к проверке managed PowerShell, а не автоматически к каждому Native-вызову. Перед запуском проверка целостности не ослаблена.

Возможное последующее улучшение — проверенный manifest ожидаемых entry hashes после живой проверки закреплённого SHA архива, с отдельной проверкой исполняемых файлов перед запуском. Автоматический status cache без проверки изменений не предлагается. Bounded startup wait мог бы уменьшить несколько ранних inspect-вызовов; exact question/nonce/authorization и unknown-barrier должны сохраниться. Эти изменения ещё не реализованы и не заявляются ускорением.

Для сопоставления нужны одинаковые задача, модель, исходники, клиент и база; холодный и тёплый запуск отдельно. Измерять wall-clock p50/p95, число tool/help/status/wait вызовов, время tools, ошибки, UTF-8 байты и фактические input/output/cached tokens из usage клиента. AgentMetrics измеряет байты/вызовы/время инструментов, но не usage модели, размышления или полное время задачи. Сумма времени инструментов при параллельных вызовах не равна wall-clock.

Перед разрешённым сценарием взять edt.status op=edt_agent_metrics args={action:baseline}; после — action=changes с тем же baseline_id. В delta входят собственные metrics и edt.help overhead; начальный tools/list не учитывается; текущий запрос учитывается после ответа. Baselines process-local, до1ч/16шт, пропадают после рестарта. Не восстанавливать отсутствующую baseline выдуманными нулями.
