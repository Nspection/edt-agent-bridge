# Единый UI-прогон и диагностика старта

Доступно с `1.4.0.20261110zzzzzzzui1`; прежний unified1 этой команды не содержит.
Проверить установленный контракт через edt.help args={action:"contract",op:"ui"}.
Десять компактных входов сохраняются. Старые Native/TestClient/Vanessa команды
доступны отдельно.

## Один запуск

```json
{"op":"ui","args":{"action":"start","project":"MyTestProject","base_uuid":"UUID_FROM_EDT","idempotency_key":"task-ui-01","capture":"final_and_failure","steps":[{"action":"open","expected_window":"My application","navigation_link":"e1cib/list/Справочник.Товары","expect":{"window":"Товары"}},{"action":"wait","expected_window":"Товары","expect":{"elements":{"ФормаСоздать":{"visible":true,"enabled":true}}},"wait_timeout_ms":3000}]}}
```

Сохранить ui_run_id/job_id. Ждать edt_operation_status с timeout_ms до25000;
это ожидание первоначального job, не повтор start. Короткий отчёт также даёт
edt.run op=ui, args={action:"status",ui_run_id:"..."}. Подробности — action=details
по тому же ID; они сохраняются ДО уборки клиента, включая полные результаты
шагов. Ссылка details_tool/details_action в summary указывает именно на
edt_ui_run, поскольку исходный журнал TestClient удаляется его cleanup.

Порядок: полная проверка плана → штатный runtime prepare с точным UUID/EQUAL →
внутренняя сессия TaskSessionService с адаптером прямого клиента → свежий
начальный snapshot → один защищённый batch → отчёт/снимки → уборка.
Начальный snapshot и client_id агент вручную не подставляет. Внутренний
session_id служит корреляцией; управлять этим прогоном через edt_ui_run,
не через прежний Vanessa-oriented edt_task_session.

Поддержаны1..16 прежних прямых шагов open/close/input/command/wait/table_*.
Каждый шаг задаёт точный expected_window. Изменяющие шаги требуют expect;
последний шаг обязательно проверяет результат (expect, wait или табличное
expect_count/expect_rows). Неизвестное действие/невалидный поздний шаг
отклоняется ДО подготовки среды и запуска клиента. Изменяющие шаги остаются
последовательными; batch не транзакция, предыдущие записи не откатываются.
По умолчанию общий I/O-бюджет worker25с, явное postcondition до10с;
их можно переопределить параметрами ниже.
Для длинных/неподдерживаемых сценариев использовать прежние пошаговые команды
или Vanessa; автоматического переключения исполнителя после отказа нет.

## Результат и уборка

Успех: terminal=true, state=completed, test_passed=true, все запрошенные шаги
подтверждены, отдельно cleanup_verified=true. Один job DONE этого не доказывает.
Отчёт разделяет итог теста и уборку. После ошибки следующие шаги не выполняются.
При outcome_unknown первоначальный результат/ссылки сохраняются; повтор start
с тем же ключом только читает историю, другой ключ не обходит неизвестный исход
или неубранные ресурсы проекта. После рестарта незавершённый прогон не запускается
заново автоматически. Неизвестность старта также не теряется при уборке.

По умолчанию auto_cleanup=true: убираются только созданные runtime-подготовкой
клиент и Python-окружение; заимствованный Python сохраняется. Данные, записанные
прикладными UI-командами, проект, база и её регистрация автоматически НЕ удаляются.
Для холодного Python создание/проверка и удаление своей среды занимают время;
готовая заимствованная среда используется повторно. Итог содержит business_data_removed=false.

При auto_cleanup=false использовать action=cleanup_preview → action=cleanup с
expected_plan_sha256. Preview включает реальный инвентарь подготовки и его hash;
изменившийся инвентарь блокирует уборку. Повтор уборки не запускает UI-действия.
Неопределённый/неполученный шаг может оставить session_closed=false: это
сохранённая история для расследования, а не обещание, что действие не выполнялось.

capture=on_failure (по умолчанию), final, final_and_failure или none. PrintWindow
сохраняет до4 видимых окон ТОЛЬКО собственного проверенного PID/времени старта,
без активации окон и без полного рабочего стола. artifacts содержит PNG paths,
blank и сведения об отдельных отказах capture; снимки не доказывают бизнес-успех.
Снимки/отчёт сохраняются для чтения после остановки клиента. Их удаление — отдельная
уборка артефактов задачи, не удаление всех runtime-snapshots workspace.

## Диагностика ожидания

Во время подготовки status содержит preparation_progress и, когда ID уже известен,
startup текущего клиента (в опубликованной ui1). В reuse1 краткий ответ
содержит startup_progress; полная диагностика после завершения сохраняется в details:

- preparation_timeline: очередь, проверка привязки, подготовка Python, запуск,
  проверка runtime; elapsed_ms, slow_preparation, slowest_stage;
- startup.startup_timeline: binding, выбор/проверка Python, worker, процесс,
  подключение протокола, готовность UI; slow_start и самая долгая фаза;
- собственный PID/время старта, protocol_connected, ошибка по типу исключения,
  число окон/видимых окон перед остановкой при доступном наблюдении;
- общие phase_timings_ms прогона, failed_stage, итог и отдельный результат уборки.

Порог slow равен10с и является наблюдением, не ошибкой и не командой перезапуска.
Длительности действующей подготовки доступны в preparation_progress; завершённые
значения фиксируются в полном журнале.
В диагностике нет командной строки, паролей, сырых пакетов и заголовков окон.
Точное окно/значения остаются в защищённом подробном результате UI-сценария.

## Медленная форма после open: дополнительное исправление

Таймаут условия теперь ограничивает начало следующих наблюдений, а не обрывает
уже начатый ответ посередине. Одно наблюдение может завершиться позже локального
wait_timeout_ms, но остаётся ограниченным wire receive и общим I/O-бюджетом операции (по умолчанию25с).
При неполном ответе на реальном транспортном лимите канал по-прежнему закрывается;
посланное действие не пересылается. Postcondition с явным expect по умолчанию
ждёт до10с вместо1,5с; готовая форма возвращается сразу. Open без expect остаётся
только подтверждением команды, не подтверждением нужной формы. Новый единый
прогон требует expect для мутаций и не принимает такой непроверенный сценарий.

В edt_form_state контракт разделяет direct/Vanessa: max_depth/group/only_visible,
endpoint/delta/pagination допустимы только для Vanessa. Direct использует свои
фиксированные пределы. Group/Page не является кнопкой для direct command;
неподдерживаемую активацию страницы выполнять отдельным поддерживаемым механизмом.

Проверка границы выполнена на независимом локальном socketpair: ответ через2с,
poll-budget1с. Worker публичного unified1 дал TimeoutError/transport_failed
через1001мс, исправленный дочитал ответ за2000мс и сохранил канал. Это
воспроизведение конкретного дефекта вложенных бюджетов, а не приёмка формы
«Секции» или произвольной тяжёлой формы TMS; пользовательская база не запускалась.

## Явные тайминги для ЦО и тяжёлых форм

Без параметров сохраняются значения: старт клиента90с, операция/весь batch60с,
явное postcondition10с (observe1500мс, wait5000мс). Готовый результат возвращается
сразу; таймаут не добавляет обязательную паузу.

- operation_timeout_s:5..300, default60. Для отдельного edt_form_action или
  edt_form_state — на верхнем уровне аргументов; для edt.run op=ui — в args.
  У batch это ОДИН бюджет на все шаги, не отдельный бюджет каждого шага.
- wait_timeout_ms:0..300000, не больше operation_timeout_s*1000. Для batch/ui
  задаётся в нужном шаге. Это предел ожидания условия, не сигнал, что карта
  действительно загрузилась: в expect нужен наблюдаемый признак готовности.
- readiness_timeout_s10..180, default90 относится только к старту клиента,
  не к последующим открытиям форм.

Для инструкции «ЦО может открываться30с, дождись до60с, общий пакет до90с»:
operation_timeout_s=90 в корне команды/прогона, wait_timeout_ms=60000 в шаге
открытия или проверки ЦО. Прямой транспорт и ожидание stdio автоматически
получают совместимый бюджет; нельзя оставить внутренний10с receive при
явно выбранном долгом бюджете90с. После команды прежние настройки транспорта
восстанавливаются. В коротком отчёте UI-run есть timing_config.

Несогласованные/дробные/выходящие за пределы параметры отклоняются ДО запуска
клиента/отправки мутаций, включая поздние шаги batch. Внутри шага отдельный
operation_timeout_s не принимается: бюджет задаётся всему пакету. Изменение
таймингов меняет payload идемпотентного ключа; неизвестный исход прежней команды
не разрешает пересылку с новым таймаутом или ключом.

В своей среде дополнительно проверен настоящий31-секундный задержанный ответ
локального socketpair с operation_timeout_s90/wait_timeout_ms45000. Ответ принят
без разрыва; базовый receive10с восстановлен. Это проверка бюджетов транспорта,
а не запуск ЦО или карты пользовательской базы.

## Сохранность результата и проверка уборки

Оригинальный журнал подготовки обязателен для подтверждения cleanup. Отсутствие
файла не доказывает, что runtime-ресурсов нет: cleanup_verified остаётся false,
ресурсы сохраняются для проверки. Полученный ответ исполнения сохраняется,
даже если последующий учёт шага/проверка привязки сессии отказали. В этом случае
task_collection_verified=false, test_passed=false; подробный исходный ответ
остаётся доступен для разбора, а не теряется при уборке клиента.


## Несколько пакетов одним клиентом

Доступно с `1.4.0.20261111reuse1`. Проверять наличие `reuse_from_ui_run_id`
в установленном контракте; прежняя ui1 этого поля не содержит.

Для одной задачи с несколькими пакетами первый `start` задаёт
`auto_cleanup=false`. После `terminal=true, test_passed=true, client_retained=true`
следующие `start` используют **новые ключи своих действий** и
`reuse_from_ui_run_id` исходного владельца. Проект, UUID и вид клиента должны
совпадать; перед действиями заново проверяются EQUAL, процесс/канал и начальная
форма. Подготовка Python и запуск процесса повторно не выполняются. При сбое
проверки замена клиента автоматически не создаётся.

```json
{"op":"ui","args":{"action":"start","project":"MyTestProject","base_uuid":"UUID_FROM_EDT","idempotency_key":"task-check-02","reuse_from_ui_run_id":"ORIGINAL_UI_RUN_ID","steps":[{"action":"wait","expected_window":"Товары","expected_form":"Справочник.Товары.ФормаСписка"}]}}
```

Все последующие пакеты ссылаются на первоначального владельца, а не друг на друга.
Один пакет использует клиент в каждый момент; уборка владельца во время пакета
блокируется. Уборка пакета освобождает только его внутреннюю сессию; его
`cleanup_verified=true` **не означает остановку заимствованного клиента**.
В конце задачи вызвать `cleanup_preview` и `cleanup` **исходного владельца**,
дождаться результата и проверить `cleanup_verified=true`. При неизвестном исходе
продолжение новыми ключами запрещено даже после уборки. После рестарта EDT старый
клиент не восстанавливается через повторный запуск.

Без явного удержания клиента прежний `auto_cleanup=true` сохраняется.
Успешный результат не доказывает, что клиент доступен сейчас: исторический status
не заменяет живую проверку очередного пакета.

Обычный status/start/job-result теперь возвращает компактный итог: ID, итог теста,
число подтверждённых шагов, индекс отказа, снимки и `diagnostic.code/next_step`.
Полные значения полей, тайминги и подробности уборки доступны через `details_call`.
Уменьшение размера JSON измеряется в байтах, не объявляется числом токенов.
Диагностика не запускает исправления и не предлагает повторять неизвестную запись.

Выбор исполнителя: Native для BSL/запросов/данных; TestClient для поддерживаемого
интерфейса; Native может готовить и проверять данные той же подтверждённой базы;
Vanessa нужна для неподдерживаемых действий либо явно выбранного сценария.
Сложность по длительности сама по себе не требует Vanessa: настраивать бюджет
ожидания формы. Существующие инструменты остаются доступны.

[Проверка повторного использования и ограничения](ui-run-reuse-validation.md).


Известный отказ UI остаётся неуспешным тестом, но полученный полный результат
собирается в журнал по исходному operation_id. Это позволяет закрыть сессию
пакета. Если закрытие не удалось, cleanup_verified=false блокирует новые пакеты;
повтор cleanup читает прежний status шага и закрывает ту же сессию, не посылая
UI-команду повторно. Неизвестный исход и несовпадающий operation_id собранными
не признаются. После успешной уборки владельца client_retained=false.
