# Подготовка информационной базы и импорт приложения

Команды используют native EDT: `IThickClientLauncher.createInfobase`, `importDtToInfobase`, экспорт конфигурации, штатный импорт проекта, `IInfobaseAssociationManager` и `IInfobaseSynchronizationManager.reloadInfobase`. Операции переиспользуют native DesignerSession/pool EDT. Создаваемому приложению закрепляется явно выбранная сборка платформы через native UPDATE installation (отдельно от launcher Version), чтобы automatic selection не открывала другую установленную сборку для той же базы. Desktop input и скриптовый запуск Конфигуратора в продукте не используются.

## Направления операций

| Задача | Команда | Что меняется |
|---|---|---|
| Создать ИБ, восстановить `.dt`, связать с проектом | `edt_infobase_provision` | Новая или явно разрешённая существующая файловая ИБ и привязка приложения |
| Полная первая загрузка проекта в восстановленную ИБ | `edt_infobase_provision(update_from_project=true)` | Всегда native `reloadInfobase`; результат требует `EQUAL` |
| Следующие обновления проекта в ИБ | `edt_diagnostics(command="update_infobase", full_reload=..., async=true)` | Схема/конфигурация ИБ; полный либо incremental-режим |
| Создать проект из ИБ | `edt_project_from_application(mode="create")` | Новый EDT-проект через native импорт и привязка исходной ИБ |
| Обновить существующий проект из ИБ | `edt_project_from_application(mode="compare")` | Отдельный снимок конфигурации и штатное сравнение; проект-получатель пока не изменяется |
| Наблюдать выполнение | `edt_operation_status(job_id=...)` | Только чтение текущего этапа, истории, результата или ошибки |

`import_project_from_infobase` сохранён для совместимости: он использует default-приложение уже существующего проекта и отдельный standalone-путь. Для явного выбора файловой базы и нового цикла используйте новые команды.

## Подготовка базы для воспроизведения бага

1. Проверьте Git-ветку, локальные изменения и разрешение пользователя на нужную базу. Создание ветки от `dev`/worktree выполняется отдельным Git-действием; backend восстановления не переключает ветки скрыто.
2. Выберите точный абсолютный путь. Для новой базы каталог должен отсутствовать. Никакие произвольные базы не выбираются по похожему имени.
3. Вызовите `edt_infobase_provision` с `dry_run=true` (по умолчанию), `project`, `database_path`, `runtime_version`, `dt_path`. Результат — план, identity исходного DT/целевой базы и `preview_sha256`.
4. Повторите те же параметры с `dry_run=false`, `expected_preview_sha256`. Смена файла/пути/параметров требует нового preview. Получите `job_id` и опрашивайте `edt_operation_status` до `DONE`/`FAILED`; сам факт постановки задания не означает успеха.
5. Проверяйте `restore_verified`, `application_bound`, `update_mode="full"`, `configuration_synchronized=true`, `equality="EQUAL"`. Если `update_from_project=false`, база только восстановлена и привязана: сохраняется признак обязательной полной первой загрузки, в том числе после перезапуска EDT.
6. Проверка равенства конфигураций не подтверждает выполнение прикладных обработчиков обновления БСП. Затем используйте обычный pipeline Vanessa/debug для проверки миграций и воспроизведения бага.

### Логин и пароль

`login`/`password` — учётные данные ИБ ПОСЛЕ восстановления DT. Они используются при проверке доступа и записываются в штатные настройки доступа приложения EDT для последующего обновления. Восстановленный DT может содержать других пользователей, чем пустая/предыдущая база.

Для `restore_existing=true` поля `existing_login`/`existing_password` относятся к СТАРОЙ базе: для её резервного DT и команды восстановления. Перед перезаписью делается native backup `before-restore.dt`; при ошибке backup загрузка DT не запускается. Непустой пароль без соответствующего логина отклоняется ещё на preview. Пароли не возвращаются в preview, status и result. Не вставляйте их в feature-файлы, команды shell или отчёты.

### Замена существующей базы и основного приложения

По умолчанию каталог базы должен отсутствовать. Замена существующей файловой ИБ требует `restore_existing=true`, исходного DT и свежего preview. При активной синхронизации отключается только связь указанного проекта с этой ИБ; связь с другим проектом блокирует операцию. Посторонние процессы 1С не завершаются: native ошибка блокировки останавливает операцию на соответствующем этапе.

Назначение новой ИБ основным приложением по умолчанию включено. Если у проекта уже другое основное приложение, нужен `replace_primary=true`; без этого операция отказывает ДО создания/восстановления ИБ. `set_primary=false` оставляет прежнее основное приложение, а полная загрузка в этом цикле всё равно направляется в явно указанную базу.

DT повторно проверяется непосредственно перед восстановлением, в том числе после длительного backup: изменившийся источник отклоняется. Одновременные MCP-восстановление и обновление одной ИБ блокируются общим guard; вложенная native full-загрузка того же задания допускается. Ключ маркера и блокировки использует нормализованный путь: регистр и разделители Windows не создают отдельную ИБ. Прежний raw-маркер той же строки подключения также распознаётся. Маркер полной загрузки снимается только после подтверждённого EQUAL.

При неуспехе смотрите `progress.stage`, `operation_directory` и журналы этапов. База не удаляется автоматически: после загрузки DT в ней могут быть важные данные. Не повторяйте restore вслепую. Выгрузки и backup содержат данные базы — храните их локально с нужными правами.

## Проект из приложения и объединение

`edt_project_from_application` принимает явные `database_path`, `runtime_version`, `login`/`password` и стандартный preview/apply.

- `mode=create`: новый `project` и отсутствующий `project_path`, заканчивающийся точным именем проекта. Конфигурация экспортируется из ИБ, импортируется штатным EDT API, ожидается BM-модель, затем приложение привязывается к новому проекту. EDT допускает только одного владельца ИБ: если база уже является приложением другого проекта, preview требует либо `bind_application=false` (привязка сохраняется), либо явный `reassign_from_project="ТочныйСтарыйПроект"`. Перенос отсоединяет только эту ИБ от указанного владельца и привязывает к новому проекту; при ошибке новой привязки, включая LinkageError SDK, предпринимается восстановление старой. Неудачная уборка частичной новой связи не отменяет попытку вернуть прежнюю; ошибки rollback показываются в очищенном сообщении задания. Переносить приложение можно только в разрешённом пользователем объёме. Данные ИБ не загружаются в Git-проект.
- `mode=compare`: `project` — существующий получатель. Создаётся собственный проект-снимок `BridgeInfobaseSnapshot...`, затем native compare с поддержкой удалений и структуры BSL. Результат `review_required` означает ПОДГОТОВЛЕННОЕ сравнение, а не завершённое обновление проекта. Опрашивайте `edt_compare(action="status")`, прочитайте tree/details, задайте план через `edt_merge_plan`, проверьте итог через `edt_merge_result` и примените через `edt_merge_apply`. Для просмотра пользователем используйте `edt_compare(action="handoff")` с тем же `session_id`. Следуйте обычным fingerprint-ограничениям native merge.

Сохранённая регистрация ИБ получает выбранную версию через native update менеджера, с сохранением её UUID, имени и прочих свойств; результат перечитывается после сохранения.

После завершения/отмены сравнения вызовите `edt_project_from_application(action="cleanup", import_id=...)`. Удаляется только собственный неизменённый проект-снимок. Повторный cleanup допускается, а отсутствие прежней сессии после close/перезапуска не мешает уборке. Если снимок участвует в другом активном native-сравнении, удаление отказывает; чужая сессия не закрывается. Проверяется всё дерево файлов проекта, включая файлы вне src. Если его редактировали, переместили или оставили несохранённые правки в редакторе, автоматическая уборка отказывает. Журналы и экспорт конфигурации сохраняются. Настоящий проект, созданный через `mode=create`, этой командой не удаляется. Для автотестов допускается явный `disposable_test_project=true` только с именем `BridgeInfobaseAudit*`: такой собственный неизменённый импорт можно убрать тем же cleanup.

Операции этого цикла пока поддерживают локальные файловые ИБ. Подключение standalone уже существует отдельной командой `connect_infobase`; этот backend не выдаёт восстановление серверной ИБ за реализованное.

Native API: [платформенный launcher](https://edt.1c.ru/dev/edt/2025.2/apidocs/com/_1c/g5/v8/dt/platform/services/core/runtimes/execution/impl/ThickClientLauncher.html), [синхронизация и full reload](https://edt.1c.ru/dev/edt/2025.2/apidocs/com/_1c/g5/v8/dt/internal/platform/services/core/infobases/sync/InfobaseSynchronizationManager.html). Сигнатуры проверяются компиляцией против установленной EDT 2026.1; документация старшей/другой линейки не заменяет эту проверку.

## Воспроизводимая проверка

`python tools/audit-edt-infobase.py --apply --dt <маленький-тестовый.dt> --runtime-version <установленная-сборка> --output .runs/creation-audit/<уникальное-имя>` создаёт только собственные disposable-проекты и ИБ. Проверяет restore/full reload, импорт приложения в новый проект, native сравнение/применение с удалением лишнего объекта, backup перед restore существующей ИБ и удаление тестовых проектов. Без `--apply` показывает план. Не используйте для этого аудита дамп с реальными чувствительными данными.

Тестовые данные можно размещать вне Git: задайте `--audit-root <абсолютный-корень>/.runs/creation-audit` и `--output` внутри этого корня. Сценарий `tools/audit-edt-infobase-recovery.py prepare|verify` проверяет существующую регистрацию, альтернативное написание пути, сохранение версии и cleanup после перезапуска отдельной EDT. Между фазами перезапускается только тестовая рабочая область. Генерируемые базы и регистрации после испытаний нужно удалять отдельно: cleanup проекта не означает удаление ИБ.
