# Задача: контекст, шаги, ожидание и уборка

Доступно с версии `1.4.0.20261108workflow8`. Набор дополняет существующие инструменты: каждую операцию по-прежнему можно выполнять отдельно.

С `1.4.0.20261109zworkflow10` новая сессия по умолчанию требует `verify_client` перед UI-шагами. Сначала запустить/подключить TestClient, затем подтвердить его привязку. Шаги запуска и проверки данных этого подтверждения не требуют.

## Один раз выбрать окружение

```json
{"action":"open","project":"TestConfiguration","profile_id":"default","endpoint":"http://127.0.0.1:9874/mcp","idempotency_key":"task-123"}
```

Для управляемого запуска с semantic UI с версии `1.4.0.20261109workflow9` доступен необязательный `manager_mcp_port` (целое 1..65535) в runner-профиль или параметры `edt_check(start)`/`edt_development_run_start`. Он запускает **уже установленное** расширение client_mcp в отдельном менеджере (`runMcp;mcpPort=...`); сессии задать тот же локальный endpoint. Без параметра прежний запуск не меняется. Это не установка расширения и не изменение доверия к EPF. Запуск резервирует порт между собственными прогонами, отклоняет занятый порт и проверяет PID слушателя. Ошибка готовности приводит к остановке собственных процессов; чужой слушатель не считается готовым менеджером. Наличие открытого порта всё равно не подтверждает каталог инструментов или личность целевого TestClient.

Передать в `edt_task_session`. Возвращённый `session_id` закрепляет расположение проекта, UUID/соединение его приложения и хеш runner-профиля. При изменении этих параметров шаги блокируются. Повтор open с тем же ключом возвращает прежнюю сессию; он не меняет привязку и не открывает базы. Пароли в сессии не сохраняются. Настройка runner и разрешение работы с выбранной тестовой базой остаются отдельными.

**Граница привязки workflow9:** API Vanessa сам по себе не даёт независимого подтверждения личности активного TestClient. `live_client_binding_verified=false` остаётся явным. Сессия фиксирует endpoint, но не превращает чужой активный клиент менеджера в правильный. Перед UI-действиями сверять тестовое окружение; точный expected_window обязателен, одинаковые заголовки сами по себе не различают базы.

## Один шаг и проверка результата

```json
{"action":"call","session_id":"task-…","step_key":"fill-name","tool":"edt_form_action","arguments":{"action":"input","element":"Наименование","value":"Тест","expected_window":"Новый элемент","idempotency_key":"name-1"},"expect":{"kind":"element_contains","element":"Наименование","text":"Тест","window":"Новый элемент"}}
```

Передать в `edt_task_step`. Проект, профиль и endpoint берутся из сессии — их нельзя переопределять в arguments. Доступны существующие edt_check (baseline/changes/receipt/start), edt_form_state, edt_form_action, edt_runtime_host и edt_test_data. Остальные команды использовать напрямую.

Проверить этот шаг:

```json
{"action":"status","session_id":"task-…","step_key":"fill-name"}
```

Сначала проверяется завершение и успех задания. Потом — явное условие по новому семантическому снимку. Поддержаны точное имя окна, наличие/отсутствие текста в элементе, наличие текста в сообщениях и пустой текст сообщений. Это проверки **текста ответа Vanessa**, а не универсальные typed-value/business assertions. Для сложного условия остаются BSL, запрос или сценарий с утверждениями. Если ответ содержит служебный текст, messages_empty не объявляет его пустым. Неполное наблюдение не подтверждает отсутствие текста.

expect поддержан только для form_action; отдельно проверить условие можно action=verify с тем же expect. Задание считается успешным только после подтверждения нижележащей операции; бизнес-результат без явного условия не объявляется проверенным.

step_key хранится на диске: повтор возвращает прежнюю постановку, изменённые аргументы отклоняются. Если ответ потерян после сохранённого намерения, результат — outcome_unknown, автоматической повторной отправки нет. Сначала расследовать через исходные инструменты. Для свежего чтения нужен новый step_key. Максимум 100 шагов и 100 ресурсов на сессию. После асинхронного prepare host вызвать status шага: он соберёт host_id в инвентарь уборки. Незабранные/неизвестные результаты блокируют закрытие и уборку.

## Ждать, не опрашивая из чата

```json
{"kind":"run","session_id":"task-…","run_id":"dev-…","after_cursor":12,"timeout_ms":20000}
```

`edt_task_wait` ждёт событие прогона до 25 секунд через уведомление сервиса и возвращает компактную страницу новых событий. Он не продолжает отладку и не принимает скриншот за агента. Старые status/cancel/continue сохранены.

Для ожидания завершения собственного шага использовать kind=operation и step_key. Для ожидания любых изменений формы — kind=form_change и after_snapshot_id из свежего edt_form_state: область и endpoint должны совпадать; ответ содержит только до 20 добавленных/удалённых строк и ссылку на полный снимок. Изменение формы само по себе не считается бизнес-успехом.

Для ожидания заданного условия формы передать kind=form и expect как у шага. Используется не более одного семантического чтения в секунду; в ответе только результат условия и snapshot_id. Это внутреннее чтение состояния, не подписка TestClient на события. Бюджет timeout_ms относится к циклу ожидания; отдельный транспортный вызов Vanessa может завершиться позже него по своему таймауту. Таймаут никогда не является успехом. Снимок при необходимости прочитать через edt_form_state(snapshot_id).

## Какую версию исходников проверяли

У development run сохраняются отпечатки исходников до обновления, перед сценарием и после завершения. edt_check(changes, run_id) и edt_task_report сопоставляют их с текущими файлами:

- `matched_at_checkpoints`: содержимое совпало в этих контрольных точках;
- `changed`: код или расположение проекта отличаются;
- `unknown_incomplete_receipt`: часть отпечатков отсутствует или неполна;
- `unknown_capture_failed`: текущий отпечаток получить не удалось.

Проверка только отпечатка доступна через edt_check(action=receipt, project=...). Область: src, DT-INF, .settings, .project; максимум 20 000 файлов, 16 MiB на файл и 256 MiB суммарно. Несохранённый файловый редактор, ссылки в исходниках и превышение лимитов не дают полного отпечатка. Крупные DT и каталоги вне этой области не читаются.

Это не атомарный снимок, не доказательство отсутствия промежуточных изменений/отката и не доказательство покрытия всех функций или версии внешних библиотек Vanessa. Исторические прогоны без отпечатков остаются unknown. runtime_verified для общего статического обзора не становится true.

## Уборка всей зарегистрированной задачи

Вызовы через сессию собирают run_id, host_id, data_run_id и set_id. Ресурсы, созданные отдельными командами, добавить явно:

```json
{"action":"attach","session_id":"task-…","resource_kind":"host","resource_id":"…"}
```

Типы: run, data_set, data_journal, host, import, database, audit_project. attach проверяет принадлежность через соответствующий сервис; декларация агента сама по себе не разрешает удаление. При preview и apply проверки повторяются.

```json
{"action":"preview","session_id":"task-…"}
```

Передать в `edt_task_cleanup`. После просмотра плана:

```json
{"action":"apply","session_id":"task-…","expected_plan_sha256":"…"}
```

Возвращает job_id для edt_operation_status. Один проход идёт по зависимостям: прогон → связанные наборы → журналы отдельных записей → host → импортированные снимки → одноразовая база → audit-проект. Незавершённая/неизвестная операция, изменённые данные или неподтверждённый ресурс блокируют последующие удаления. Для продолжения получить новый preview; асинхронное удаление данных продвигается по одному защищённому шагу. Новые fixture-узлы в уборке не создаются. Физического удаления отдельных деловых записей нет: только mark_deletion по старым проверенным рецептам.

Для автоматического удаления **новой файловой** базы при edt_infobase_provision явно указать disposable_test_base=true. Отдельный шаг удаления той же базы доступен как edt_infobase_cleanup(action=preview|apply, owned_base_id, project, base_uuid): apply требует expected_plan_sha256 и возвращает job_id. Команда не принимает произвольный путь.

После создания сохранить owned_base_id и добавить его как resource_kind=database в сессию, открытую для этой базы. Сервис проверяет локальное подтверждение создания, личность файла через NTFS hard link, привязки других проектов, отсутствие занятого файла и неизменность плана. Приложение/запись запуска удаляются через API EDT, настройки приложения — через Eclipse preferences только для UUID этой базы; затем каталог атомарно переносится в служебный quarantine на том же диске и удаляется оттуда. При отказе остатки сохраняются для проверки и безопасного продолжения. Другие операции с той же базой/проектом блокируются общей блокировкой EDT Agent Bridge. Оставшиеся после ошибки файлы проверяются перед продолжением; подменённая база и новые файлы сохраняются для разбора. Размер и время изменения файла 1CD остаются строгими; исключение допускает только завершающую запись в уже существовавшие файлы журнала 1Cv8Log/<14 цифр>.lgp/lgd/lgf, без появления новых файлов. Требуется файловая система с hard links.

Существующие базы и серверные ИБ не получают такую возможность физического удаления. Для серверной базы нужна отдельная явная операция администрирования; она не маскируется зелёным итогом. Сессия также не сертифицирует уборку незарегистрированных ресурсов и побочных эффектов обработчиков.

После завершения вызвать edt_task_session(action=close). Закрытие с незавершёнными ресурсами/неизвестными шагами отклоняется. Историю/доказательства в metadata сессия сохраняет; это не файлы Git.

## Проверки и ограничения

Java-регрессии, отдельная EDT и границы живой проверки описаны в [task-sessions-validation.md](task-sessions-validation.md).

Текущие прогоны сохраняют каноническую личность соединения (`base_identity_format=connection-v1`). Старый файловый прогон без этого маркера допускается только при совпадении проекта, UUID, текущего канонического пути и исторического хеша реального пути. Серверные и неподтверждённые старые привязки таким исключением не принимаются; неизвестные шаги автоматически не повторяются.

Живая приёмка task-step/wait/cleanup с настоящей Vanessa: [task-vanessa-live-validation.md](task-vanessa-live-validation.md).
