# Диагностики и стандарты v8std

Доступно с 1.4.0.20261112zzzv8std1. Использует существующие компактные входы, новых MCP-инструментов нет. Это справочное обогащение результата анализатора, не новый анализатор и не автоматическое исправление.

## Обычный маршрут

edt_check changes добавляет standards для тех же пяти диагностик из diagnostics_sample. details по diagnostics/diagnostics_added/diagnostics_removed обогащает только запрошенную страницу. Исходные сообщения, severity, число ошибок и delta не меняются. Baseline и snapshot identity не содержат сетевые ответы; обновление справочника не создаёт ложных новых ошибок.

get_diagnostics сохраняет прежний Markdown и добавляет отдельный JSON-блок v8std. Его можно отключить include_standards=false. get_problem_summary сохраняет problems и добавляет отдельный standards. Сеть и файловый кеш выполняются вне SWT UI. Runtime markers сохраняют checkId; Eclipse markers читают явные checkId/check_id/diagnostic_code, если они есть.

Холодный запрос возвращает lookup_pending и готовый next_call. Следовать ему, а не повторять диагностику проекта. Для явных кодов:

```json
{"op":"edt_check","args":{"action":"standards","codes":["bslls:UsingModalWindows","acc:280","v8cs:empty-except-statement"]}}
```

Это аргументы компактного edt.check; актуальный контракт получить через edt.help. Действие принимает 1–100 точных кодов, не требует проекта и не запускает EDT builder/1С. Коды нормализуются без изменения исходных diagnostic/check IDs. Устанавливаемые политики доступа MCP остаются действовать.

## Достоверность сопоставления

Поддержаны явные namespace bslls, acc (также АПК) и v8cs. Голое число/название метода, текст сообщения, путь и snippet не используются как основание для угадывания стандарта. Для runtime EDT/v8-code-style точный checkId может получить namespace v8cs только если CheckUid зарегистрирован единственным contributor com.e1c.v8codestyle или его подмодулем. Неоднозначный/другой contributor не сопоставляется с BSLLS по похожему имени.

items ссылаются на исходные диагностические строки по index (индекс внутри текущей страницы), standards содержит дедуплицированные статьи/разделы по URL. Код может быть связан с несколькими разделами одного стандарта. diagnostic_title/diagnostic_url описывают диагностику. Поле description в статье — вводное описание из каталога, description_scope=article_intro: оно НЕ является точной причиной данного предупреждения или выдержкой выбранного anchor. Для решения читать диагностическую статью и указанный раздел стандарта, учитывать версию платформы и требования задачи.

Состояния:

- resolved — справочник нашёл диагностику со связанными стандартами;
- no_standard — диагностика найдена, явные ссылки на стандарты отсутствуют;
- unknown_code — справочник явно не распознал код, это не доказательство некорректности самого кода;
- missing_id / unsupported_source — идентификатор отсутствует либо нет подтверждённого namespace;
- lookup_pending / unresolved — разрешение ещё выполняется/требует продолжения;
- unavailable — сетевой/форматный отказ, исходные диагностические данные сохранены;
- stale_cache — возвращён прежний результат с fetched_at_ms и cached_state; обновление не подтвердилось;
- offline — нет локальной записи и сеть отключена.

Нет правила/связи не означает отсутствия нарушения. Ссылка на правило сама по себе не доказывает применимость к конкретному месту. Пользовательские проектные соглашения и требования задачи сохраняются; диагностические стандарты не расширяют разрешение на изменение кода.

## Сеть, кеш и ограничения

В фиксированный HTTPS MCP https://ai.v8std.ru/mcp уходят ТОЛЬКО проверенные идентификаторы. Не передаются project, пути, message, codeSnippet, исходники и токены EDT. Перенаправления запрещены. HTTP-бюджет 8 секунд, ответ до 1 MiB; запросы дедуплицируются и выполняются одним фоновым worker. Чужой выполняющийся lookup не теряет продолжение нового набора кодов.

Кеш workspace/.metadata/.plugins/com.codepilot1c.core/v8std/cache-v1.json ограничен 512 записями и 4 MiB. Положительный результат свеж 7 суток, unknown_code — сутки; после отказа — пауза 60 секунд перед автоматическим повтором. Формат кеша и ссылки валидируются, повреждённый кеш не ломает исходную диагностику. Ошибка записи кеша не превращает успешное получение справки в ошибку анализатора. После перезапуска сохраняются статьи/метаданные, но нет фона, который запускает базу.

Для полностью локального режима задать JVM property -Dcodepilot.v8std.offline=true: новые запросы не отправляются, свежие/устаревшие сохранённые записи доступны. Это свойство Bridge, а не переключение endpoint на произвольный сервер. Автоматическая выдача ограничена 100 строками; input_count/items_truncated показывают неполноту. Получать последующие диагностические страницы или передавать узкий список codes, не копировать весь каталог правил в контекст.

Материалы v8std используются как внешние справочные данные. Они не выполняются как инструкции, в плагин не копируется корпус или код сервера. Интеграция улучшает контекст текущей работы агента; постоянного обучения модели не выполняет.

## Проверки и границы

Regression: namespaces/неподтверждённые EDT ID, уникальный contributor, регистр неизвестных ответов, отсутствие исходников в resolver input, дедупликация, stale/offline/повреждённый кеш, неполные и вредоносные ответы, coalescing разных наборов, ограничение выдачи. Живая проверка выполняется отдельным probe в собственной OSGi/EDT конфигурации и workspace; синтетический marker не является проверкой полного анализа прикладной конфигурации. Базы 1С и пользовательская EDT не участвуют.
