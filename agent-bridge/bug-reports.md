# Баги и предложения через GitHub

Агент может отправить описание любой проблемы Bridge или предложение в Issues открытого `Nspection/edt-agent-bridge`. Отдельный сервис и общий токен не нужны.

## Вход и разрешение

В настройках **EDT Agent Bridge → Багрепорты в GitHub** нажмите **Подключить GitHub**. Откроется вход в браузере. После подтверждения в GitHub в EDT появится имя подключённого аккаунта. Для ручного входа нажмите **Войти с токеном…**. Кнопка **Создать токен** откроет форму GitHub, а готовый токен можно вставить в защищённое поле EDT. Пароль вводится на сайте GitHub. Пароль и токен не передаются через чат или MCP.

Вход в EDT использует Git Credential Manager из Git for Windows. Если компонент отсутствует, кнопка **Открыть баг-репорт на GitHub** открывает форму нового Issue. Текст нужно заполнить и отправить на GitHub. Учётные данные сохраняются в Windows Credential Manager отдельно для каждой рабочей области. Каждая новая попытка входа использует отдельную запись: отмена или ошибка сохранения настроек сохраняет прежнее подключение. Старые настройки продолжают работать без повторного входа. OAuth-права показывает GitHub; они могут быть шире Issues. Для PAT нужны подходящие права создания Issues в целевом репозитории; classic `public_repo` даёт более широкий доступ. Fine-grained PAT подходит не для всех участников публичного репозитория. Вход через браузер предпочтителен.

После входа выберите политику:

- **Не отправлять** — публикация запрещена.
- **Подтверждать каждый отчёт** — пользователь видит точный публичный текст и нажимает **Отправить в GitHub**. Эта кнопка сама отправляет отчёт; отдельный `submit` агенту не нужен.
- **Разрешить агентам очищенные отчёты** — без отдельного окна разрешены только структурированные технические коды и счётчики. Произвольные описания багов и предложений всегда требуют просмотра и подтверждения.

Лимит — 5 новых отправок в сутки на рабочую область. Смена подключения или политики отменяет старые разрешения; черновик нужно обновить и показать заново.

## Маршрут агента

Получайте текущую схему через `edt.help` для `edt_bug_report`; используйте возвращённые entry/op/args.

1. `status` показывает локальную настройку. `account_live_verified=false` означает, что этот ответ не выполнял запрос к GitHub; это не ошибка сохранённого подключения. `verify_account` асинхронно проверяет `/user`, но не доказывает право создания Issue.
2. Если нужен вход, вызовите `auth_start` с `method=choose` и устойчивым `idempotency_key`. Пользователь сможет войти через браузер или с токеном. Для сразу открывающегося браузерного входа используйте `method=browser`. При отсутствии Git Credential Manager результат `browser_report_opened` означает, что открылась форма GitHub для ручной отправки (`report_submitted=false`). Читайте `request_status` по возвращённому `next_call`.
3. `prepare_async` принимает `component=testclient|native|editor|mcp`, `report_type=bug|proposal`, `title`, `description`, устойчивый ключ. Для технического отчёта описание необязательно; передавайте только известные поля `diagnostics`. Для локального журнала TestClient передайте `client_id` и `operation_id` без `diagnostics`: существующее действие не повторяется.
4. Дождитесь результата через `request_status`, затем выполните возвращённый `review_request` с `report_id`, `expected_payload_sha256`, ключом. Пользователь проверяет текст и нажимает кнопку отправки.
5. Проверяйте квитанцию: только `state=submitted` и `issue_url` подтверждают публикацию. Legacy `prepare`, `submit`, `reconcile` сохранены; для долгих операций предпочтительны `prepare_async` и `submit_async`.

Повтор одного ключа возвращает исходную квитанцию без нового окна или повторной работы. Для намеренной новой попытки после отменённого входа используйте новый ключ. Не используйте новый ключ для обхода неизвестного результата отправки.

## Публичный текст и доставка

Коды и счётчики диагностики фильтруются по разрешённому списку. Описание, предоставленное агентом, помечается соответствующим образом и не считается подтверждённой диагностикой. Известные шаблоны секретов удаляются, но автоматическая очистка не гарантирует удаления всех личных данных: проверяйте текст перед отправкой. Сырые логи, код, файлы и снимки автоматически не прикладываются.

Доставка сначала проверяет аккаунт и политику, затем сохраняет claim до единственного POST. Ответы 401/403/404/422 сохраняют черновик с причиной отказа, снимают прежнее разрешение и требуют нового просмотра даже в автоматическом режиме; квота возвращается после сохранения отказа. Ошибки сети, потеря ответа, 429 и 5xx оставляют `delivery_unknown`. Автоматический повтор запрещён. `reconcile` только читает до 500 последних Issues и ищет совпадение автора и полного текста; отсутствие совпадения не доказывает отсутствие публикации.

Успешные квитанции хранятся отдельно от pending для дедупликации. До 200 pending-отчётов; неизвестный исход не удаляется автоматически. Повреждённая запись сохраняется локально в карантине, её ID постоянно блокируется до ручного расследования; остальные отчёты продолжают работать. Исходный повреждённый текст не выдаётся через MCP и не публикуется.

Автоотправка означает явный вызов агентом по разрешённой политике. Фоновой отправки каждого исключения и автоматического исправления новых Issues нет.

Официальные контракты: [GitHub Issues API](https://docs.github.com/en/rest/issues/issues#create-an-issue), [GitHub PAT](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens), [GCM configuration](https://github.com/git-ecosystem/git-credential-manager/blob/main/docs/configuration.md).
