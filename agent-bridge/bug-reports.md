# Багрепорты агентов через MCP

С версии `1.4.0.20261113reports1` агент может подготовить технический отчёт и создать Issue в открытом репозитории `Nspection/edt-agent-bridge`. Отдельного сервиса и общего токена в поставке нет.

## Разовая настройка пользователем

В настройках **EDT Agent Bridge → Багрепорты в GitHub** нажмите **Подключить GitHub**. Нужен Git for Windows с Git Credential Manager в стандартной установке. Авторизация открывается только этой кнопкой; MCP не может открыть login или включить обмен данными. Используются отдельный namespace GCM `edt-agent-bridge` и Windows Credential Manager. OAuth-права показывает GitHub; они могут быть шире Issues. Отключение отчётов не удаляет Git-учётные данные пользователя.

Выберите политику и сохраните настройки:

- **Не отправлять** — начальное состояние.
- **Подтверждать каждый отчёт** — агент готовит draft; кнопка **Просмотреть и разрешить отчёт** показывает точный публичный текст и SHA256. После согласия агент выполняет `submit`.
- **Разрешить агентам очищенные отчёты** — отдельное подтверждение в настройках разрешает агентам публиковать только структурированную диагностику без каждого нового вопроса. До 5 новых отправок в сутки в этой EDT.

Смена аккаунта или политики требует нового preview. Выключение до durable dispatch запрещает отправку; уже отмеченный `sending` запрос считается начатым и не отзывается задним числом.

## Контракт агента

Используйте `edt.help` для установленного контракта `edt_bug_report`. Действия:

1. `status` — локальная настройка или сохранённая квитанция по `report_id`. Показанный аккаунт — сохранённая настройка; это не живая проверка GitHub.
2. `prepare` — `component=testclient|native|editor|mcp` и `diagnostics`. Неподдерживаемые поля и значения отбрасываются. Источник помечается `agent_reported`.
3. Для подтверждённой локальной операции TestClient передайте `component=testclient`, `client_id`, `operation_id`, без `diagnostics`. Читается сохранённый журнал без повтора действия. Его детали переживают stop, но не cleanup.
4. Проверьте возвращённые `title`, `body`, `payload_sha256`. `submit` принимает `report_id` и `expected_payload_sha256`. Разрешение пользователя проверяется отдельно.
5. `reconcile` читает GitHub после `sending`/`delivery_unknown`. Совпадение автора и полного текста с уникальным маркером восстанавливает квитанцию. Проверяется не более 500 последних Issues; отсутствие совпадения оставляет исход неизвестным.

Автоотправка здесь означает вызов агентом по заранее разрешённой политике. Фоновой отправки каждого исключения и автоматического чтения/исправления новых Issues нет.

## Что попадает в открытый Issue

Версия Bridge, компонент, вид и фаза сбоя из фиксированных списков, состояние канала, флаги unknown/block и ограниченные числовые счётчики. Произвольный текст, exception message, стек, имена проектов и баз, пути, URL, код, файлы, снимки и credentials не поддерживаются. Сырые логи не загружаются. Дополнительное описание пользователь может добавить сам в GitHub.

Одинаковый аккаунт, версия и нормализованный вид сбоя дают один `report_id`; изменившиеся тайминги, счётчики и индекс шага не создают дубликат. Дедупликация локальная для этой EDT, не глобальная между пользователями. Отчёт не гарантирует установление корневой причины.

## Доставка и история

Сначала атомарно сохраняется claim, затем выполняется единственный POST. Потеря ответа, ошибка сети или незавершённый claim дают `delivery_unknown`; автоматический повтор запрещён. Новый ключ не используется для обхода неизвестного исхода. Ответы сервера, тела ошибок и токены не включаются в MCP-ошибку репортера.

Квитанции успешных отправок сохраняются для дедупликации и не расходуют лимит pending. До 200 неподтверждённых/подготовленных отчётов; unknown не удаляется автоматически. Заполненный pending требует расследования и reconcile, а не удаления журнала. Служебная история хранится в metadata собственного workspace. Изменённые записи, текст или хеш блокируют публикацию.

Проверки выполняются с поддельным transport: утечки, отзыв согласия во время ожидания credentials, смена аккаунта, concurrent submit, crash/timeout после POST, tamper, дедупликация, квоты и reconcile. Публичный тестовый Issue автоматически не создаётся; живой OAuth/POST у другого пользователя требует его подключения.

Официальные контракты: [GitHub Issues API](https://docs.github.com/en/rest/issues/issues#create-an-issue), [GCM configuration](https://github.com/git-ecosystem/git-credential-manager/blob/main/docs/configuration.md).
