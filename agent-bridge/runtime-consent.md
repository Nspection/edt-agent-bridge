# Разрешение запуска и использования TestClient / Native

Сборка `1.4.0.20261112zzzzzzzzconsent11` вводит два независимых слоя подтверждения: разрешение MCP на запуск/использование конкретного runtime и отдельное решение живого стартового вопроса платформы.

## Разрешение MCP

Начать с `edt.status`, затем `edt.help` с `args.action=contract` для `edt_test_client`, `edt_runtime_host`, `prepare` или `ui`; выполнить возвращённый entry/op/args. Отсутствие разрешения возвращает `awaiting_consent`, `process_started=false` и готовые варианты решения. Клиент агента должен сначала получить явное разрешение пользователя. Вызов `consent_apply` является утверждением клиента о таком разрешении, а не криптографическим доказательством личности пользователя.

Политики: `once` — один запуск и использование созданного сеанса; `remember` — следующие запуски того же scope; `deny` — запрет. `consent_preview` → `consent_apply(expected_plan_sha256)` использует свежий хеш плана. `consent_status` показывает scope и ревизию. `consent_revoke_preview(consent_id)` → `consent_revoke(consent_id,expected_plan_sha256)` отзывает разрешение. При revoke передавать только consent_id и параметры операции, без host_id/project.

Scope включает проект и реальный путь, контекст, UUID привязанной/основной ИБ и хеш её идентичности. Для TestClient закреплены вид клиента, executable и SHA256; для Native external — точный путь/хеш EPF, ZIP Native и шаблон host. Новая EPF требует нового разрешения. Metadata-host и FULL-обновление базы остаются отдельным ранее согласуемым механизмом.

Разовый grant потребляется перед запуском. Его lease действует для дальнейшего использования этого сеанса. Отзыв немедленно блокирует новые действия и resume; чтение статуса, наблюдение, stop/cleanup сохраняются. Повторная выдача разрешения не оживляет прежний lease. Разрешение MCP не меняет защиту/доверие платформы.

## Стартовые вопросы платформы

`startup_inspect` доступен до подключения runtime и возвращает распознанный вопрос, exact question hash, варианты решения и требуемое authorization. Поддержаны проверенные русские вопросы 8.5 для собственной EPF (`external_epf_trust`) и её Native-компоненты (`native_component_for_module`). Пароли, лицензии, сертификаты, произвольные security-окна и бизнес-диалоги этим маршрутом не обслуживаются.

`startup_answer` требует exact authorization (UUID базы, scope hash, question hash, allow/deny, `allow_foreground_input=true`) и устойчивый idempotency_key. Проверяются PID/start/executable, живое окно, поколение HWND, дерево вопроса, файлы и ревизия разрешения непосредственно перед вводом. Координаты вызывающий не задаёт. Для проверенной кнопки используется один защищённый клик, поскольку UIA Invoke в проверенной 1С не выполняет действие. Решение отдельно журналируется. Уход окна и готовность канала проверяются независимо; факт отправки input не означает готовность.

Если Windows не разрешила foreground и доказано, что input не отправлен, ответ может вернуть `awaiting_foreground` и continuation_call для **того же ключа** (не более трёх попыток). Повторное решение того же уже отвеченного вопроса запрещено. Неизвестный исход дополнительно блокирует следующие ответы и использование runtime. Успешный ответ допускает отдельное решение следующего распознанного вопроса и работу после подтверждённой готовности. Ошибку/неизвестный исход не обходить другим ключом, новым host или повторным start.

После allow использовать возвращённый resume; после deny — stop/cleanup. Resume продолжает исходный запуск и не повторяет бизнес-пакет. Unified prepare/ui сохраняют исходные ресурсы и ожидающее действие; выданный next_call ведёт к исходной подготовке.

**Ограничение TestClient:** реальный вопрос безопасности запуска тестирования в проверенной среде не появился, в том числе в отдельной пробе без подавления стартовых диалогов. Автоматический ответ для его неподтверждённого шаблона не заявлен: `manual_required`, решение вручную, затем resume. Разрешение MCP для TestClient полностью поддержано и проверено. Подтверждение Native-компоненты может сохранить доверие к модулю в платформе; отзыв MCP его не отменяет.

Native DLL/протокол 2, проверенный vendor TestClient и шаблон HostForm не менялись. Успех выполнения Native: terminal=true, state=completed, execution_success=true; readiness канала сам по себе этого не доказывает.

## Native startup: фоновый собственный вопрос (audit25)

`startup_inspect` и `startup_answer` сохраняют прежние контракты и exact-question authorization. Разрешение `allow_foreground_input=true` включает временное поднятие собственной группы окон, безопасный клик в пассивную область для активации, затем один ответный клик. Это не произвольные координаты или управление другими приложениями. После input обязательны наблюдение исчезновения вопроса и отдельная проверка Native runtime; ответа `success=true` недостаточно для готовности host.

При occlusion адаптер создаёт durable visibility lease. Java восстанавливает прежний уровень окна после завершения или убийства helper. Изменённый PID/start/nonce, foreign owner/capture/menu и зажатые кнопки блокируют ввод. Неясный результат не повторяется. После отказа до input следовать только original continuation_call, если он возвращён. Проверено на собственном Native external Windows x64/1С8.5.1.1522: обе платформенные проверки, running и terminal info через MCP без ручной активации. Другие security templates остаются manual_required.
