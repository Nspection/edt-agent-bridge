# Popup-снимки и изолированный Native-клиент

Начиная с 1.4.0.20261113zpopup1 новый Native-host по умолчанию запускает свой клиент на отдельном невидимом рабочем столе Windows (`presentation=isolated`). Создание выполняется до первого окна клиента. Переключения пользовательского рабочего стола и автоматического перехода к visible нет. Существующие host сохраняют свой режим, а его смена требует остановки клиента. Refresh переносит подтверждённый режим; legacy-host без сохранённого режима получает isolated в плане замены.

Для одноразовой интерактивной настройки доверия можно явно выбрать `presentation=visible` при prepare/start. Startup input на isolated desktop недоступен: плагин сообщает ограничение и не показывает окно поверх пользователя. После подготовки остановить host и явно перезапустить isolated. Защита 1С/Windows не отключается. TestClient и редакторы EDT этим параметром не управляются. stdout/stderr изолированного клиента не захватываются; остаются штатный client.log 1С и startup stages.

Для исчезающего popup использовать один client execute шаг:

```json
{"action":"execute","host_id":"HOST_ID","execution_mode":"batch","idempotency_key":"menu-check-001","steps":[{"context":"client","kind":"execute","code":"// открыть меню своей тестовой формы","screenshot":true,"screenshot_expect":"popup"}]}
```

Получать точный контракт через edt.status → edt.help. До исполнения проверяются `host_features=batch_popup_capture_v1` и `native_features=armed_popup_capture_v1`. Старый custom Native может выполнять обычные поддерживаемые операции; запрос обязательного popup без нужных capabilities отклоняется до отправки BSL.

Наблюдение включается до BSL. Событие показа нового captionless WS_POPUP текущего UI-потока запускает немедленный захват собственных поверхностей в память. Их композиция учитывает Z-порядок и координаты; промежутки чёрные, изображение рабочего стола не считывается. Проверяются PID верхних и видимых вложенных окон. Captioned-карточка или дочернее поле не завершают ожидание меню. Кадр сохраняется после закрытия popup; дальнейшая отправка не требует его видимости.

Окно наблюдения — 5 секунд. `screenshot_expect=popup` допустим только для client execute со screenshot=true, не для wait/server. Синхронные BSL и same-thread WM_PRINT нельзя прервать этим сроком; ограничение не является общим таймаутом GUI. Сбой/исчезновение popup даёт snapshot_error и failed batch с сохранённым результатом уже исполненного шага. **Не повторять изменяющий BSL ради снимка.** При ошибке кода screenshot_on_failure снимает текущее окно, не ожидает меню и не использует ранний кешированный кадр.

Обычный `КомпонентаАгента.Screenshot()` снимает текущее состояние и не потребляет вооружённый кадр. Новые ArmScreenshot/CaptureState/CancelScreenshot/TakeArmedScreenshot расширяют ABI, прежние IDs 0–6 сохранены. Лимиты PNG/host не изменены. В квитанции есть capture.scope, window_count/popup_count, armed, реальное captured_at и отдельное upload_received_at. `popup_count` — количество дополнительных собственных поверхностей, не число пунктов меню. `pixel_content_verified=false` требует осмотра изображения агентом; корректный PNG не доказывает текст и порядок элементов.

Проверено в собственных чистых файловых ИБ: толстый управляемый Native-клиент 8.3.27.2325 и 8.5.1.1522, меню из Alpha/Beta/Gamma. Отдельный actual-DLL тест закрывает Win32 popup до отправки и проверяет три цветные строки в PNG, 60 create/close desktop и сохранение desktop вызывающего потока. Это не проверка всех окон, GUI-потоков, конфигураций TMS или серверных баз. Все тестовые клиенты/EDT остановлены, две одноразовые базы удалены штатно по ownership lease. Закрытые исходные fixtures и неисполняемые журналы оставлены в собственной тестовой области для воспроизведения.
