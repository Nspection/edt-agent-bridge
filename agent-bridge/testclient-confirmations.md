# Прикладные подтверждения прямого TestClient

С `1.4.0.20261112zzzzzzzdialogs4` доступен узкий маршрут через прежний `edt_test_client` / `edt.run op=edt_test_client`: `dialog_inspect` и `dialog_answer`. Это отдельный разовый ответ уже обнаруженному прикладному диалогу, а не восстановление неизвестного ввода.

## Когда доступен ответ

После полного отрицательного ответа изменяющей команды worker сохраняет исходные диагностику и outcome_unknown. Только при рабочем канале, нуле ожидающих протокольных ответов и полностью прочитанном стандартном `MessageBox85` он сразу связывает диалог с исходным operation_id. Более позднее постороннее окно не может стать этим диалогом. Таймаут, неполный кадр, ошибка чтения и not_sent не создают разрешения на ответ; скрытого resync/reconnect нет.

Поддерживаются 2–3 точно видимые и доступные кнопки Да/Нет/Отмена или Yes/No/Cancel. Скрытые служебные кнопки исключаются. Неизвестная доступность, неподдерживаемая кнопка, отсутствующий handle, смена текста/набора кнопок/экземпляра формы блокируют ответ. Текст, идентичность окна/формы и кнопок проверяются повторным ограниченным чтением перед CLICK. Vendor, GUID и двухкадровый action/commit не изменены.

## Короткий цикл

1. Читать результат исходной операции. `dialog_available=true` даёт `next_call` для `dialog_inspect` с точными client_id и blocking_operation_id.
2. `dialog_inspect` возвращает текст, доступные кнопки, dialog_hash, UUID базы и `decision.options[].next_call`. Это варианты для явного решения пользователя, не разрешение автоматически выбрать «Да». Для сформированного заранее собственного тестового сценария решение может входить в его уже согласованный объём.
3. После явного разрешения выполнить ровно выбранный вариант `dialog_answer`. В запросе нужны client_id, base_uuid, blocking_operation_id, dialog_hash, точное имя button, idempotency_key и `authorization={application_confirmation:true,base_uuid,blocking_operation_id,dialog_hash,button}`. Разрешение разовое, без wildcard и сохранённых общих правил. Изменение любого поля разрешения отклоняется до отправки.
4. Читать форму/данные и исходный результат отдельно. `answer_acknowledged=true` означает только подтверждение ответа диалогу. `original_outcome_unknown=true`, `mutation_blocked=true`, `postcondition_verified=false` сохраняются. Исходный input не повторяется, общий barrier не снимается и новая обычная мутация не разрешается.

У ответа отдельная долговечная запись. Тот же ключ с тем же запросом читает сохранённый результат даже после stop; другой ключ для того же диалога не создаёт повтор. Прерванный или неизвестный ответ не повторяется. Cleanup удаляет детали по прежним правилам.

## Границы

`MessageBox85` — общий renderer, а не классификатор безопасности. Известные темы безопасности/доверия/пароля/лицензии дополнительно отклоняются по тексту, но denylist не доказывает прикладную природу вопроса. Агент обязан получить явное семантическое разрешение на конкретный прикладной вопрос; platform security, trust, password и license обрабатываются вручную и не входят в этот контракт. Поле application_confirmation — явное утверждение вызывающего клиента, не независимо удостоверенный токен пользовательского согласия.

Первая версия не разрешает автоматическое продолжение исходной операции, снятие barrier, произвольные модальные формы или сохранённые разрешения. Даже доказанное наблюдением значение поля не переписывает исходный неизвестный протокольный результат. Дальнейшее восстановление требует отдельного проверенного контракта.

У единого UI-прогона сохраняется прежняя уборка клиента после неуспеха. Для этого интерактивного решения использовать собственный прямой TestClient, сохранить исходный operation_id и ответить до cleanup; ссылка в старом результате после cleanup не является живым разрешением.
