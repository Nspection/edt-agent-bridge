# Экономный цикл Native и локальная актуальность

С 1.4.0.20261112zznativeflow4. Число компактных входов MCP не увеличено. Native DLL, ABI, HTTP endpoints, WinHTTP и HostForm.bsl не изменены.

## Выполнить один раз, затем наблюдать

execute/result по умолчанию возвращают компактный вид: host_id/request_id, state/terminal/outcome_unknown, execution_success (null без доказанного результата), phase, reported_steps, failed_step, artifact_count, новые краткие записи шагов и квитанции снимков. Значения BSL/запросов не копируются в каждый опрос. Небольшой успешный результат обычного BSL/запроса до1024 UTF-8байт JSON сразу доступен как value/value_inlined, включая null; для большего стоит value_in_details и используется details_call. Значения шагов batch остаются в details.

Полный прежний результат сохраняют action=details и action=result/execute с compact=false. null, ошибки, outcome_unknown, полные значения и snapshot manifests не удаляются из сохранённого запроса. Внутренний NativeHostService.result и команды чтения данных/проверок сохраняют свой полный контракт. Обновлённым агентам предпочтителен компактный путь; прежним сценариям, ожидающим execution.success/value прямо из result, следует передать compact=false.

Выполнить исходный execute ровно один раз. Далее отправлять возвращённый next_call как готовый объект tool/arguments. Во время выполнения он ведёт к wait; при наличии следующей страницы — к result; failed/outcome_unknown ведут только к details первоначального запроса. У завершённого успехом пакета без следующей страницы next_call отсутствует. Ни один из этих маршрутов не предлагает новый execute, смену ключа или создание host для повторения BSL.

wait ограничен timeout_ms 0..25000, по умолчанию 20000. Это ожидание изменений, а не таймаут исполнения BSL и не отмена. Оно отпускает monitor канала и не занимает UI EDT. Очередь/delivered, переход этапа/шага, новый завершённый шаг, снимок или terminal outcome являются изменениями; рост attempts/elapsed/sequence внутри той же проверки — нет. Без cursor wait сначала берёт текущую точку и возвращает текущую страницу после изменения/таймаута; с cursor немедленно возвращает уже накопленные изменения. При таймауте timed_out=true, успех не выдумывается.

## Курсоры и снимки

result/wait принимают cursor и page_size 1..16 (по умолчанию 8). Курсор связывает host/request и хеши уже показанных шагов/снимков; содержит только идентификаторы и хеши, не BSL/параметры. Прочитанные страницы не повторяются, новые шаги выдаются через new_steps, новые квитанции снимков — new_artifacts. Курсор не разрешает исполнение и не влияет на бизнес-результат. При перезапуске он проверяется по сохранённым данным; после удаления/изменения истории возвращается явная ошибка, не пустая успешная история. Новый запрос не создаётся.

Краткая запись шага сохраняет success/outcome_unknown/failure_kind/value_omitted и ограниченное сообщение ошибки. Она не доказывает успех всего пакета. Квитанции снимков помечены verification=capture_receipt_only и не содержат непроверенный путь. artifacts_call использует прежний snapshots для повторной проверки PNG/SHA и получения путей; grid/grid_step остаются доступны. Это позволяет wait проверять маленькие manifests без повторного хеширования всех PNG на каждом timer tick.

## Кто следит за актуальностью

Плагин сопоставляет локальные required_native_release/SHA/protocol/features с архивом своего host, проверяет неизменность собственных исходников и нормализованный fingerprint шаблона. Версия Bridge и версия Native — разные: несколько релизов Bridge могут использовать один совместимый Native ZIP. Совпадение не требует сети или перезапуска. Статус показывает actual_native_sha256 отдельно от recorded_native_sha256; протокол выводится как доказанный только для известного pinned архива. Явно проверенный custom ZIP сохраняется как custom, его протокол не угадывается.

Проверка включена в status и перед новым execute. Несовместимость блокирует отправку BSL и возвращает структурированный state=blocked/execution_state=not_dispatched с готовым ensure_current. action=ensure_current проверяет package/template; при полном совпадении changed=false, current=true, runtime_ready отдельно подтверждает running. При отсутствии/устаревании подготавливает проверенный pinned cache и предлагает refresh_preview; сам не заменяет живой host. prepare_package/configure_package и явный native_path+expected_native_sha256 по-прежнему доступны.

## Обновить host через MCP

refresh_preview проверяет привязку/владение, незавершённые и неизвестные исходы, затем возвращает plan_sha256 и apply_call. Для metadata план также включает fingerprint всех сохранённых src текущего проекта; его изменение отклоняет старый хеш до остановки клиента. Preview не является транзакцией или блокировкой редакторов на весь процесс обновления. Для metadata явно требуется allow_database_update=true: удаление старой и загрузка новой обработки FULL-обновляют базу всем текущим проектом. Preview по умолчанию не подставляет это разрешение. Существующее разрешение пользователя можно передать; команда не должна выдавать его сама. Для external обновления базы нет. Пакет заранее скачивается/проверяется до остановки старого клиента. Custom ZIP сохраняет исходную доверенную SHA256 и не заменяется managed молча; повреждённый custom блокирует refresh до выяснения.

refresh замораживает приём новых заданий только после долговечного claim, сохраняет новый host_id ДО model factory, выполняет стандартную ownership cleanup и prepare/start. execute/start/cleanup согласованы по per-host locks; новый host не исполняет BSL до завершения исходной замены. queued/delivered/outcome_unknown блокируют замену, а не отменяются ради неё. Восстановление не повторяет неизвестный бизнес-запрос.

refresh_status хранит исходные old/new IDs и этап отказа. Повтор refresh возвращает исходную запись и не запускает замену снова. После перезапуска незавершённая замена — outcome_unknown без automatic_resume. completed/launch_accepted означают принятый запуск нового клиента; readiness_verified=false требует отдельного status с running. Новый host также показывает parent_refresh_state/execution_blocked_by_refresh.

При refresh старые requests/снимки сохраняются на прежних путях (results_retained=true), доступны details/cursor/snapshots/grid. Код/параметры исходных запросов остаются в приватной истории до явного cleanup старого host. Такой cleanup проверяет сохранённый хеш и удаляет только старую историю; новый host не закрывает. Изменённая история сохраняется для разбора. Уборка нового host выполняется отдельно; бизнес-данные не откатываются.

## Проверки и измерение

Сравнивать один исходный request: старый full-result polling и новый compact next_call/wait, считая число вызовов и UTF-8 bytes JSON-результатов. Discovery, подготовка и JSON-RPC envelope учитываются отдельно. Это измерение объёма ответов, не точных токенов и не общего ускорения EDT. Runtime-приёмка выполняется в собственной базе; пользовательские EDT/ИБ не участвуют.
