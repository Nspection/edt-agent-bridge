# Короткий цикл агента: workflow11

Доступно с `1.4.0.20261109zworkflow11`. Наличие и схемы проверять у установленного MCP. Низкоуровневые команды сохранены; новые команды не расширяют разрешённый проект/базу и не меняют доверие платформы.

## Найти команды без повторного каталога

`edt_capabilities` по умолчанию больше не добавляет все маршруты. Для них явно передать `include_workflows=true`. Старые `name_contains`, `category`, пагинация и `include_schemas` сохранены.

```json
{"names":["edt_task_batch","edt_operation_status","edt_task_session"],"include_schemas":true,"include_descriptions":false}
```

До 32 точных имён; отсутствующие возвращаются в `missing_names`. Сохранить `catalog_sha256` и при последующем подключении передать `if_catalog_sha256`: при совпадении ответ содержит `not_modified=true` без повторных схем. Это хеш всего каталога, а не отдельного запроса: совпадение не означает, что ранее были получены схемы ещё не запрошенных имён. Для новых имён запросить схемы отдельно. Хеш включает имена, описания, категории, mutating и схемы с точными числами; не подтверждает readiness, права или соединение с базой.

## Дождаться готовности

```json
{"required_tools":["edt_task_batch","edt_check"],"project":"TestConfiguration","database":"equal","timeout_ms":20000}
```

Это `edt_ready`. Без проекта проверяются сервисы и команды; при указанном проекте дополнительно проверяется его модель. `database=none|bound|connected|equal`, по умолчанию `none`. SDK EDT подтверждает контейнер синхронизации проекта, но не подключение выбранной ИБ: поле `synchronization_container_present` не является per-base proof. В текущей реализации `connected_verified=false`, `connection_state=unverified_sdk_container_only`, поэтому `database=connected` остаётся blocked. Для проверки привязки использовать bound, для равенства конфигурации — equal. Посторонние загружающиеся проекты не блокируют выбранный проект. `runner_configured=true` проверяет сохранённую настройку, а не живую Vanessa. Команда ничего не запускает, не подключает и не обновляет. `ready=false`, `blockers`, `unknown_sections` и `timed_out` остаются явными. До доступности MCP использовать существующий HTTP health endpoint. Лимит ожидания — 25 секунд; длительность одного native чтения дополнительно зависит от EDT.

## Получить итог фонового задания

```json
{"job_id":"JOB_ID","timeout_ms":20000,"compact":true}
```

`edt_operation_status` ждёт уведомления о терминальном состоянии, не ставит задание заново и не отменяет его по таймауту. Без `timeout_ms` старый опрос сохранён. Короткий ответ включает этап, ошибку, `terminal`, `result_available` и разрешённые итоговые ID/флаги из `result`; логи и исполняемый код в него не копируются. DONE не означает успешный бизнес-результат. Неизвестный/истёкший ID — ошибка, а не разрешение повторить запись.

## Управлять объёмом ответа

У capabilities, ready, operation_status, task_session, task_step, task_wait, task_report и agent_metrics есть общий необязательный `response`:

```json
{"action":"resume","session_id":"task-…","response":{"view":"summary","fields":["steps","pending_resources"],"max_bytes":8192}}
```

Без него сохранена прежняя форма ответа, кроме отдельно описанных изменений capabilities и добавленных полей. С ним возвращаются `data` и `response`. `view=summary|details`, `fields` выбирает верхнеуровневые поля, `max_bytes` ограничивает сериализованный JSON полезной нагрузки (1024..131072). Это не лимит всего транспортного MCP envelope. Флаги успеха/неполноты и evidence не убираются ради проекции; в известных контейнерах результатов сохраняются и вложенные outcomes (например result.execution.success=false). Если они сами не помещаются, возвращается `state=details_required`, без ложного успеха или ошибки уже выполненного действия.

Пропущенные данные доступны по `response.details_id`:

```json
{"details_id":"detail-…","offset":0,"limit":4000}
```

Это `edt_result`. Выдаёт неизменяемый JSON как текст страницами: продолжать по `next_offset`, проверять `has_more`. Частичная страница не доказывает отсутствие данных. Смещения — UTF-16, суррогатные пары не разрезаются. Вложенные ошибки ограничены 1024 символами с *_truncated; на пределе глубины возвращаются evidence_truncated=true/evidence_complete=false, а не исходный payload. Кеш только в памяти: 30 минут, максимум 64 записи/16 MiB, до 2 MiB на запись. После перезапуска/вытеснения ID недоступен; команда ничего не переисполняет. Для слишком больших ответов возвращается явная недоступность деталей; применять исходные status/пагинацию, а не повтор изменяющей команды.

## Выполнить несколько шагов

Открыть обычную `edt_task_session`, проверить client binding для форм. Затем:

```json
{"action":"advance","session_id":"task-…","batch_key":"edit-item","timeout_ms":20000,"steps":[{"step_key":"name","tool":"edt_form_action","arguments":{"action":"input","element":"Наименование","value":"Проверка","expected_window":"Новый элемент","idempotency_key":"name-1"},"expect":{"kind":"element_contains","element":"Наименование","text":"Проверка","window":"Новый элемент"}}]}
```

`edt_task_batch` выполняет 1..16 последовательных шагов через существующий task executor. Поддержаны `edt_check`, `edt_form_state`, `edt_form_action`, `edt_data_assert`. Для каждого действия формы обязательно `expect`. Операции host и test-data оставлены отдельными командами: факт постановки их сложных операций сам по себе не доказывает завершения.

Сохраняются fingerprint плана, внутренние ключи шагов, текущий индекс и квитанции. Исходные arguments/код/учётные данные пакет дополнительно не сохраняет. Для продолжения `advance` снова передать **тот же** план и ключ. Изменённый план отвергается. Уже подтверждённые шаги не отправляются повторно. `status` наблюдает текущий шаг и может собрать его завершение, но не отправляет следующий.

Пакет останавливается при ошибке, невыполненном expect, смене привязки или неизвестном исходе; это не транзакция и не откат данных. `timeout_ms` задаёт бюджет между native вызовами/опросами; один нижележащий вызов может длиться дольше. `running` продолжать тем же планом; `outcome_unknown` расследовать через исходную операцию, не обходить новым ключом. Сохраняются лимиты task-session: 100 шагов, 100 ресурсов, до 32 пакетов.

## Продолжить после нового чата или перезапуска

`edt_task_session(action=resume,session_id=…,offset=0,limit=20)` возвращает текущую проверку binding, страницы записанных шагов, ссылки на результаты, состояния пакетов и оставшиеся ресурсы. `last_status`/квитанции исторические; это не новое выполнение и не подтверждение текущего бизнес-состояния. При дрейфе `binding_current=false`. Никакой автоматической загрузки старого плана объединения или повторной отправки операций нет.

## Ошибки и измерения

В новых маршрутах и task/status family ошибки содержат `tool`, `stage`, `reason`, `retry_safe`, `execution_state`. Общая классификация не утверждает, что запись не состоялась: для изменяющих действий по умолчанию `retry_safe=false`, `execution_state=not_proven`. У ошибки фонового задания это вложенный `failure`; исходный job ID и состояние сохранены. Не все исторические инструменты переводятся на новый формат этим изменением.

`edt_agent_metrics` возвращает накопленные счётчики процесса: вызовы, байты JSON запросов/ответов, длительность и ошибки по инструментам. Payload/аргументы/командные строки не сохраняются. Сравнивать два снимка; чтение самого счётчика учтётся после выдачи ответа. Это не фактические токены, стоимость модели или полный сетевой трафик. Счётчики сбрасываются при перезапуске.
