# Проверка TestClient на TMS_FILE85 после локальной установки

10 ноября 2026. После отдельного разрешения пользователя установлена тестовая
1.4.0.20261110zzzzzprepare1 в его EDT (workspace TMS), затем EDT перезапущена.
Перед закрытием активных редакторов не было; закрытие штатное, без force kill.
Проверка p2 выполнена сначала на копии профиля. Реальный p2 install завершился
успешно; установленный код/ресурсы идентичны проверенному preparedev6 кроме
манифестов версии. Резервные config/profile — .runs/install-unified-tms/backup.
Публичный релиз и GitHub Pages не изменялись.

После перезапуска модель стала READY, но native equality было NOT_EQUAL.
Read-only refresh дал NO_CHANGES/NOT_EQUAL без обновления. Получено отдельное
разрешение пользователя загрузить весь текущий TMS_GIT (bugfix/000528453) в
TMS_FILE85. Штатный incremental update завершился EQUAL; UUID базы сохранён:
3eed4be3-5de5-4e2f-91c6-e33aa27ebe50. Бизнес-исходники агент не менял.

Повтор старого compact1 сначала подтвердил прежний отказ: 1cv8c без окон,
ready timeout за ~14 секунд от старта job. На новой сборке через edt.run op=prepare
с engine=testclient/client_kind=thin/readiness_timeout_s=90 протокол подключился,
но первый UI-probe вернул transport_failed. Подготовка остановилась без повторов,
state=outcome_unknown, startup_phase=waiting_for_ui, observations=1. Причина
транспортного отказа не установлена; это не доказательство отсутствия поддержки
тонкого TestClient в 1С. Таймаут90 секунд не был исчерпан.

После полной уборки именно этой подготовки отдельно запущен толстый управляемый
TestClient с client_kind=thick. Тот же проект/UUID/платформа8.5.1.1522: ready=true,
connected=true, live_client_binding_verified=true, ui_ready=true, окно за6482мс
после протокола. edt_form_state transport=testclient/view=windows прочитал
начальную форму TMS; PrintWindow показал главное окно «[КОПИЯ] AXELOT SCM.
Компонент TMS X5 - Клиент тестирования». Бизнес-команды/записи не отправлялись.

Обе собственные подготовки убраны через cleanup_preview/hash/cleanup;
state=cleaned. Python был borrowed и сохранён, чужие клиенты/Native hosts не
останавливались. Обновлённая EDT оставлена запущенной. Процедура доказывает
рабочий толстый путь, но не приёмку всех бизнес-функций и не исправление
глубинной причины отказа тонкого клиента. Тонкий TestClient поддерживается
платформой и проходил собственную синтетическую базу на той же версии.

## Тонкий клиент: исправление вложенного ожидания (thinfix1)

Локально установлена 1.4.0.20261110zzzzzzthinfix1. Дефект кода подтверждён:
DirectClientStartup имел общий бюджет90с, но передавал ready-пробам максимум10с;
worker одновременно ограничивал receive10с и всю команду25с, stdio —35с.
Неполный ответ дольше10с превращался в transport_failed и закрывал канал,
не позволяя использовать оставшиеся80с. В thinfix1 только стартовый ready
получает весь оставшийся бюджет1..180000мс на wire и ограниченный stdio budget
(+15с, максимум195с). Обычные observe/wait остаются0..10000мс. Неизвестный
ответ не повторяется, новый клиент/толстый fallback автоматически не запускаются.
Тип ошибки теперь сохраняется в startup_diagnostics.reason без текста ответа.

Исходный отказ был плавающим: дополнительный прямой thin-запуск на prepare1
тоже прошёл. Из старого статуса нельзя восстановить тип исключения первого
transport_failed. Поэтому дефект вложенных таймаутов исправлен и проверен,
но не объявляется безусловно установленной причиной каждого исторического отказа.
Гипотеза обязательного ожидания Win32-окна перед attach не подтвердилась:
контрольные thin-запуски с задержанным и немедленным attach прошли. Такой
обход в продукт не добавлялся. Диагностика не сохраняла командную строку,
пароли или сырые пакеты; первая диагностическая копия завершилась из-за
ошибки Unicode в чтении аргументов и была исправлена до дальнейших проб.

После установки: три последовательных edt_test_client(action=start,project=TMS_GIT)
без client_kind и один edt.run(op=prepare,intent=ui) без engine/client_kind.
Все четыре выбрали thin/1cv8c.exe; ui_ready=true, connected=true,
live_client_binding_verified=true. В каждом edt_form_state(view=windows)
успешно прочитал живую начальную форму TMS. Готовность после протокола:
6553, 6022, 6006, 5996мс.

Приёмка: 773 Java-теста,35 worker-тестов,16 table-тестов, standalone boundary,

отправлялись; это приёмка запуска/чтения, не всех прикладных сценариев.
База повторно не обновлялась, новый source/config metadata не добавлялся.
Три прямых клиента и aggregate-клиент убраны штатно, cleaned=true;
заимствованный Python сохранён. Финальный summary: TMS_FILE85 UUID
