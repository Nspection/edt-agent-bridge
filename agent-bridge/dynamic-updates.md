# Динамическое обновление через MCP

Доступно с релиза `1.4.0.20261111zzzdynamic1`. Контракт получать через установленный `edt.help`; предыдущий zzupdates1 ещё не содержит эти действия.

`edt.run` → `edt_update_control` возвращает `update_dynamic` в `allowed_actions` только для распознанного штатного вопроса исключительной блокировки с единственной активной кнопкой «Обновить динамически». Это ответ тому же native update, а не вторая загрузка. SDK определяет, допускает ли набор изменений динамическое применение. Защита FULL/EQUAL не отключается; неподдерживаемое изменение остаётся отказом платформы.

## Разовое разрешение и разрешение на задачу

Получить исходный `update_id` и свежий `pending_question_sha256` через прогресс исходного job или `list`/`status`. Выполнить `action=update_dynamic` с `update_id` и аргументом `expected_question_sha256`, передав в него свежий `pending_question_sha256` из наблюдения. Не передавать pending_question_sha256 как имя входного аргумента. Команда считается явным разовым выбором; постоянная запись не создаётся.

Если пользователь уже поручил «всё делай сам, обновляй и запускай» для выбранного проекта/базы, агент может выполнять такие разовые ответы в рамках этого поручения без повторного вопроса. Не превращать разрешение на задачу в постоянную настройку. При отсутствии разрешения показать пользователю варианты. Доверие/подписи/прочие окна безопасности этот механизм не обслуживает.

## Постоянное разрешение

Только при явной просьбе пользователя разрешать это постоянно:

1. `policy_preview(project, policy=allow_dynamic)` возвращает точный scope и `plan_sha256`.
2. `policy_apply` с теми же полями и `expected_plan_sha256` сохраняет разрешение. Сохранить `policy_id`.
3. Сохраняемое разрешение применяется к уже ожидающим собственным вопросам и будущим обновлениям с той же привязкой. Оно не запускает обновления само.

Scope включает абсолютный путь проекта, контекст ветки EDT, UUID основной базы и хеш целевого соединения. Другая база/ветка/проект не наследует разрешение. Пароли и строка соединения не записываются. Операция фиксирует исходный scope до SDK-вызова. При каждом динамическом ответе перепроверяются исходные путь/контекст/UUID/target, native-окно, хеш, доступность кнопки и действующие MCP exposure/mutation policy. Разрешение новой ветки не применяется к уже ожидающему обновлению старой. Повреждённое хранилище закрывает автоматическое продолжение.

## Отзыв

Для текущей привязки использовать `policy_preview(project, policy=ask)` → `policy_apply` со свежим хешем. Для сохранённого разрешения после смены ветки/отвязки базы: `policy_revoke_preview(policy_id)` → `policy_revoke(policy_id, expected_plan_sha256)`. Этот путь не обращается к базе. Отзыв предотвращает будущие автоматические ответы, но не откатывает уже начатое обновление.

## Проверка результата

Завершение job ответа означает отправку выбора, а не успешное обновление базы. Дождаться исходного job, проверить его результат и native equality. В прогрессе доступны `last_answer`, источник `explicit_once_command` / `scoped_persistent_permission`, revision разрешения и `dynamic_update_selected`. `runtime_clients_reloaded_verified=false`: старые открытые клиенты не считаются автоматически перепроверенными; при необходимости запускать свежий собственный клиент.

Не обходить неизвестный исход новым ключом или повторным update. Истёкший/изменённый хеш и чужой диалог не принимаются. Отмена исходного собственного вопроса по-прежнему доступна после смены привязки.

## Проверки и ограничения

866 Java-тестов и 57 Python-контрактов прошли; standalone boundary проверена. Ревью и независимое ревью нашли P2: разрешение нового контекста B могло принять pending update контекста A при том же UUID/target. Исправлено захватом полного исходного scope и его перепроверкой; независимый harness на финальной сборке подтвердил отказ в обоих направлениях drift. Отмена после drift сохранена. Новых подтверждённых P1/P2 не найдено.

На финальной сборке в новой собственной файловой базе 8.5.1.1522 проверены: отказ устаревшего хеша, разовый native dynamic во время FULL/reloadInfobase со строгим EQUAL, выдача постоянного разрешения при уже открытом диалоге, автоматический ответ следующему matching update и отзыв по policy_id. После отзыва следующий диалог остался ждать и был отменён. Изменялся синоним справочника; несовместимые структурные изменения и кластер не проверялись. Reload открытых прикладных форм не заявляется.

Финальный удерживающий клиент — обычный собственный тонкий 1С с проверенными PID/start-time/целевым путём; Python этому механизму не нужен. Попытка подготовить TestClient до этого завершилась отказом venv из-за Windows/MSIX-перенаправления LocalAppData; клиент и UI-шаги тогда не запускались. После подтверждения отсутствия дочерних процессов создавшееся именно этим прогоном Python-окружение убрано, журналы сохранены. Это ограничение подготовки тестовой среды, не скрытая успешная проверка TestClient.

После перезапуска private EDT первый incremental вернул known SDK already_connected. Исходная ошибка и UUID зафиксированы, состояние прочитано; восстановление выполнено отдельным FULL/reload с dynamic и строгим native EQUAL. После него pending/future incremental-сценарии прошли. Неизвестная бизнес-операция не повторялась; тестовая база не содержала бизнес-записей.

Собственные клиент, база, регистрация и проект убраны, тестовая policy отозвана и архивирована; настройки private EDT/UI preferences восстановлены. Программный FULL-probe отключён и в продукт не включён. Пользовательские EDT/базы/порт1552 не изменялись. Пакет проверяется p2 verifyOnly на собственной копии профиля; после merge сверяется с кандидатом, после публикации проверяются обычные публичные URL/SHA256 и p2 resolver.
