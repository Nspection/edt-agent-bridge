# EDT Agent Bridge 1.4.0.20261113reports3

Проверены реальный вход GitHub, создание Issue через MCP и TestClient 8.3.27.2325 в собственной изолированной EDT и новой одноразовой базе. Пользовательская EDT, базы и x5 не изменялись.

- GitHub credentials теперь изолированы по workspace; явный login выбирает нужный аккаунт. После обновления с reports1/reports2 требуется повторное подключение GitHub в каждом workspace и новая подготовка/подтверждение черновиков в состоянии `prepared`. Для `sending`/`delivery_unknown` — только `reconcile` с исходным аккаунтом.
- GCM и проверка аккаунта выполняются до durable claim и расхода квоты. Единственный POST использует ту же проверенную сессию; неизвестный исход по-прежнему не повторяется. Подтверждение точного текста и смена policy/account остаются защищены повторной проверкой.
- Отчёт сохраняет фактические фиксированные коды worker, включая protocol rejection status code, без сырых сообщений и данных базы. Отдельный acceptance_test формирует фиксированный тестовый текст без произвольных публичных полей.
- После cleanup preparation больше не выдаёт исторический running/connected runtime как текущий. Собственный остановленный клиент отмечается cleaned/connected=false, заимствованный сохраняется, частичный результат не заявляет готовность. Resume удаляет прежнюю причину ожидания согласия.

Реальный OAuth выполнен штатным GCM browser flow; [Issue №35](https://github.com/Nspection/edt-agent-bridge/issues/35) создан через MCP, автор и полный текст независимо сверены через GitHub API. До разрешения отправка блокировалась; повторный submit вернул тот же номер. Тестовый Issue затем закрыт. Вход и точное разрешение вызывались production service из непоставляемого интеграционного модуля собственной EDT; физические SWT-кнопки и диалог не проверялись.

TestClient: фактическая версия исполняемого файла 8.3.27.2325, открытие списка, выбор строки по коду 00000000002 (235 мс, postcondition_verified=true), ФормаНайти с последующим наблюдением UniversalListFindExtForm, ввод в Pattern и Cancel с проверенными постусловиями. Канал остался usable, mutation_blocked=false. Проверена также unified preparation с разовым согласием и уборкой; собственные клиенты и одноразовая база удалены, заимствованный Python сохранён. Это не воспроизведение прикладного документа TMS: пользовательские данные не использовались. Read-only current-row table_describe на 8.3.27 остаётся явно неподдержанным; native table_select работает.

1238 Java, 179 Python, 33 PowerShell controller + 3 CLI + 13 startup проверок; OSGi, boundary/provenance и p2 verifyOnly на копии профиля. Собственное и независимое Astra medium ревью изменений завершены; подтверждённые замечания исправлены. Историческая классификация удаления Касперским остаётся неизвестной; исключения и настройки защиты не менялись.
