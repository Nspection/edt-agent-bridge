# Поиск и пакетное чтение контекста

С 1.4.0.20261112zzzzzcontext1. Новые компактные инструменты не добавлены: используются прежние `edt_search_in_code` и `bsl_get_method_body` через возвращённый `edt.help` entry/op/args.

## Совместимость поиска

Отсутствующий searchType по-прежнему означает text. Явные text и regex сохраняют прежние формат, порядок, подстрочные совпадения, нечувствительность к регистру, scope и прежние ограничения выдачи. Ни ранжирование, ни top_k к ним не добавлены. Прежний BM25 также доступен явно. Для точной фразы с пробелами использовать text; для шаблона — regex. Auto не распознаёт намерение искать regex.

`searchType=auto` — opt-in для первого поиска реализации: простой Unicode-идентификатор, в том числе с точками/подчёркиваниями, ищется как буквальная подстрока через text; остальные формулировки идут в BM25. Это консервативная лексическая эвристика, не разрешение символа и не понимание смысла. Например, dotted имя ищется целиком и может не совпасть с отдельным именем декларации. Все явные режимы доступны агенту для уточнения.

```json
{"projectName":"Demo","query":"проверка доступности склада","searchType":"auto","scope":"modules","top_k":5}
```

Ответ сообщает requested_search_type, selected_search_type и route_reason. Для auto text возвращаются первые top_k строк (1..20, default5), has_more и complete_scan: при дополнительном совпадении сканирование останавливается, total_results — только число возвращённых строк, не полный счётчик. Snippet не длиннее1200 UTF-16 единиц, snippet_truncated явен. Чтобы получить прежний набор совпадений и порядок, вызвать явный text без top_k. Буквальные совпадения в вызовах не являются именами/диапазонами деклараций методов.

Auto BM25 наследует [квоты и свежесть BM25](project-bm25.md). После20с возможен terminal=false/job_id/next_call; опрашивать исходный job, не запускать поиск повторно. Route metadata относится к первому ответу; terminal result фонового задания сохраняет search_type=bm25 и не обязан повторять auto metadata. rebuild допустим только для выбранного BM25-маршрута, обычно не нужен.

## Пакет методов

После выбора нужных методов:

```json
{"projectName":"Demo","items":[
 {"filePath":"CommonModules/Orders/Module.bsl","name":"ПроверитьОстатки"},
 {"filePath":"src/CommonModules/Orders/Module.bsl","name":"ПодготовитьОтгрузку"}
],"max_chars":16000}
```

items содержит1..8 объектов. Общий projectName; поля элемента filePath/name обязательны, kind=any|procedure|function, start_line — точная строка декларации для неоднозначного имени, context_lines=0..20. BM25 line — строка декларации; не подставлять start_line фрагмента с комментариями/аннотациями. При усечённом имени метода сначала разрешить настоящее имя. Для text/regex сначала определить нужный метод, а не передавать строку совпадения как декларацию.

Batch принимает пути внутри src и src/...; обратные слеши нормализуются. Абсолютные пути, .., пустые сегменты и переопределение проекта запрещены. items взаимоисключён с одиночными filePath/name/kind/start_line/context_lines. Весь запрос проверяется до первого чтения. max_chars — строгий integer2000..40000, default16000, только batch. Прежний singleton и его40000-символьное усечение сохранены.

Каждый элемент вызывает тот же BslSemanticService, что и одиночное чтение. Результаты сохраняют порядок, index, success и method либо error. AMBIGUOUS_METHOD не выбирает первый метод автоматически; возвращается до8 кандидатов и candidates_truncated. Ошибка элемента не скрывает остальные, terminal=true и успешная оболочка ToolResult не означают успех каждого элемента: проверять failed_items/truncated_items/complete.

Общий бюджет охватывает возвращённые тексты методов вместе с маркерами пропуска, но не JSON-оболочку/метаданные и не точное число токенов. Остаток делится между оставшимися элементами; крупный первый метод не съедает весь пакет. text_truncated/original_body_chars/returned_body_chars явны. Усечённый head/tail — excerpt; startLine/endLine продолжают описывать исходный диапазон, не сплошной текст excerpt. Если нужно больше текста — запросить метод отдельно; singleton тоже усечёт тело после40000, поэтому проверить truncated и при необходимости читать точный диапазон исходника. Batch не снижает максимальный размер прежнего singleton.

Источник batch — текущая семантическая модель EDT. atomic_snapshot=false: методы читаются последовательно, это не атомарная транзакция всего пакета; сохранённый индекс поиска и текущая модель могут различаться. Чтение не сохраняет редакторы, не меняет исходники, не запускает/обновляет ИБ. Native/TestClient/Vanessa не задействованы.

## Проверка экономии

Разделять реальную runtime-приёмку и controlled retrieval→read benchmark. Совпадение ответа со старой версией доказывает совместимость контрактов, но не успешное решение бизнес-задачи агентом. В сравнении считать исходные поиски/чтения, pending polls отдельно, реальные компактные JSON body и время; cold индекс отдельно от warm. Усечение не выдавать за бесплатное сохранение всей информации или измерение расходов LLM.

Медленный batch ожидается до20с, затем terminal=false/state=reading/job_id/next_call ведёт к edt_operation_status исходного задания. Следовать продолжению без повторной отправки items. Работа идёт в отдельной bounded очереди с одним worker; обычные background jobs не занимают её очередь. В конечном result проверять failed_items/truncated_items/complete. Количество семантических чтений не уменьшается, пакет экономит roundtrips, а не гарантированное время SDK-парсера.
