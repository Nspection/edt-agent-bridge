# Приёмка единой подготовки runtime

10 ноября 2026. Ветка codex/unified-runtime-preparation. Работа локальная,
без коммита, пуша, релиза и установки в пользовательскую EDT.
Собственная EDT Agent Bridge Dev, MCP 8769, 1С 8.5.1.1522 Windows x64.

## Реализовано

- edt.run op=prepare → canonical edt_runtime_prepare, прежняя авторизация и
  отдельная проверка exposed зависимостей. До десяти компактных входов сохранены.
- Явный project/base_uuid/intent/idempotency_key. Проверяются контекст проекта,
  target identity, UUID и EQUAL; один native refresh без загрузки конфигурации.
  Никаких автоматических update/bind/trust или бизнес-действий.
- Управляемый Python и собственный TestClient; внешний Native host; проверка
  существующего профиля/менеджера Vanessa с блокером при нехватке настроек.
- Журнал резервирует IDs до создания процессов/native-объектов. Повтор ключа
  не запускает заново; другой ключ не обходит неизвестный/незавершённый исход
  в том же проекте. Отдельный Native-помощник допускается у известного ready UI.
- Живая готовность проверяется повторно. Уборка — preview/hash, только созданные
  ресурсы, клиент/host перед Python; borrowed ресурсы сохраняются.
- Общая тяжёлая очередь с native-host/infobase: подготовка и её уборка не
  конкурируют с ними за EDT-модель. Лёгкие чтения/статусы продолжают работать.

## Первичная ассоциация UUID

Созданы только собственные audit-проект и disposable файловая база вне home и
workspace. После provision служебный одноразовый fixture bundle точечно отключил
свою ассоциацию штатным NativeInfobaseGateway.detachApplication. У UUID перед
продуктовым вызовом подтверждены associated=false, owners=[], primary_uuid="";
глобальная регистрация и saved runtime оставались на месте.

edt_infobase_bind preview/apply создал ассоциацию и primary по UUID;
binding_verified=true и session summary подтвердили нужную базу/EQUAL.
Проверена именно ветка первоначального associate, а не только setDefaultInfobase.
Fixture bundle не входит в исходники/дистрибутив продукта, удалён после теста.
Живой проект синтетический, без Git; смена branch context отдельно покрыта
контрактами. Это не приёмка всех вариантов EGit/серверных баз.

После рестарта SDK возвращал NOT_EQUAL и один transient отказ refresh.
Подготовка завершилась до создания ресурсов, клиент не запускался. Отдельный
разрешённый native incremental update только собственной fixture установил
EQUAL; после него финальная подготовка прошла. Prepare сам обновление не делал.
Эта ситуация и неполная диагностика SDK-refresh остаются явной границей:
blocked/needs_update требует разбора исходного состояния, а не слепого нового ключа.

## Живой runtime

Один prepare сам подготовил pinned/hash-verified Python и запустил TestClient.
Повтор того же ключа вернул тот же client_id, новый ключ отказал в дубликате.
Проверены блокеры: нет native ZIP, нет Vanessa-профиля, previous outcome_unknown,
неверный UUID; запусков и ресурсов для этих проб не было.

На финальном кандидате проверены оба явных вида клиента:

- thin: ui_ready/connected/live binding=true, окно примерно за 1144 мс после
  подключения протокола;
- thick: 1cv8.exe с SDK RunModeManagedApplication, окно примерно за 355 мс.

Для каждого прошёл batch из 9 шагов: открыть список, создать, заполнить,
сохранить, открыть повторно, сверить значение и закрыть. Все postconditions
подтверждены, сохранённый полный результат и повтор idempotency key проверены.
Снимки обоих окон просмотрены; имена Preparation v5 acceptance и
Preparation thick acceptance сохранились в списке своей базы.

Native-помощник через unified prepare создал один внешний host и собственный
процесс. Живой status показал awaiting_runtime, ready=false. Снимок подтвердил
штатный запрос доверия EPF; доверие не изменяли, повторного запуска не было.
Host и внешний проект затем удалены. Живой Native-ready с разрешённой компонентой
в этой работе не заявлен; ready/unknown/start-once покрыты контрактами.
Vanessa проверена на явном отсутствии профиля; живой готовый менеджер не запускали.

## Сообщённый отказ TMS_FILE85

Пользователь передал отказ compact1: thin подключился к протоколу, окна не было,
старый worker ready завершился после 10 секунд. Пользователь уточнил: при уже
обновлённой базе обычный старт занимает менее 10 секунд. Поэтому таймаут не
объявлен установленной причиной TMS. Пользовательская EDT/база не запускались.

Добавлены ограниченное ожидание того же процесса (90 с, настраиваемо 10..180),
повтор только известных read-only condition_timeout, немедленная остановка при
транспортной неопределённости, явный client_kind thin/thick без fallback.
В status сохраняются startup_phase, protocol_connected, startup_diagnostics.
Неотправленные UI-команды не доказывают отсутствия прикладной инициализации;
неудачный запуск не объявляется retry_safe. Случай TMS с отсутствующим окном
на его реальной конфигурации не воспроизведён и не считается исправленным.
