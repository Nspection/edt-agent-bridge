# Короткий рабочий цикл агента

Доступно начиная с выпуска `1.4.0.20261108workflow5`.

## Сначала сводка

```json
{"project":"TestConfiguration"}
```

Передать в `edt_session_summary`. Ответ содержит готовность модели EDT, имя/UUID выбранного приложения и синхронизацию базы, состояние отладки и наличие сохранённого профиля Vanessa. Указание `run_id` добавляет короткий статус именно этого прогона; принадлежность проекту проверяется. Неизвестные секции перечислены отдельно и не означают готовность. Команда ничего не запускает, не подключает базу и не открывает окна. Наличие профиля не подтверждает живую готовность Vanessa. Все сеансы, процессы, изменения исходников и модальные окна команда не инвентаризирует; для окон есть `edt_process_snapshot`.

## Запуск проверки одной командой

```json
{"action":"start","project":"TestConfiguration","profile_id":"default","idempotency_key":"task-123-check-1","update_db":true,"feature_paths":["C:/tests/check.feature"],"visual_checkpoint":true}
```

Передать в `edt_check` только после разрешения работы с выбранной тестовой базой. Сначала настроить профиль через `edt_runner_profile` и подготовку менеджера; повторно передавать пути и учётные данные не нужно. `update_db` обязателен: агент явно выбирает, обновлять ли базу. Обновление включает изменения проекта. База и проект проверяются существующим исполнителем; новая команда использует тот же цикл, защиту повторного запуска, отдельный менеджер Vanessa и очистку собственных процессов. Самостоятельно создавать базы, готовить доверие, исполнять произвольный BSL или удалять деловые данные она не начинает. Для visual checkpoint существующий исполнитель требует один обычный сценарий.

## Короткий статус и события

```json
{"action":"status","run_id":"dev-…","after_cursor":0}
```

Ответ содержит этап, итоговые счётчики, ошибку, текущий шаг, контрольную точку и до 20 новых событий. Для следующего запроса передавать возвращённый `event_cursor`; `latest_cursor` — последняя известная позиция, `has_more_events` — есть следующая порция. `events_gap=true` означает, что часть истории уже вышла из окна хранения: нельзя считать выборку полной. Без новых событий список пуст. Полные журналы и результат не копируются в краткий ответ. Длинные ошибки и сообщения обрезаются с явным флагом `_truncated`; полный текст доступен отдельной командой.

- Остановка отладчиком → `edt_debug_inspect`, затем штатные команды отладки.
- Визуальная проверка → просмотреть снимок из `checkpoint`, затем `edt_development_run_continue` с актуальными managed run ID, checkpoint ID и SHA256. Короткая команда не подтверждает просмотр автоматически.
- Полные детали → `edt_development_run_status(run_id=...)`.
- Отмена → `edt_check(action="cancel",run_id=...)`; останавливает собственный прогон, без отката данных.
- После перезапуска незавершённый прогон отражается как `interrupted_by_restart`; старый работник не возобновляется и действия автоматически не повторяются. Проверить состояние контроллера перед заменой прогона. Для новых прогонов ключ запроса сохраняется на диске: повтор start после перезапуска возвращает прежний прогон, изменённые аргументы с тем же ключом отклоняются. Если запись ключа есть, а снимок утрачен, возвращается outcome_unknown без повторного исполнения. Для прогонов, созданных до появления сохранённых ключей, эта гарантия не заявлена.

Существующие команды `edt_development_run_status` и `edt_operation_status` принимают `compact=true`. По умолчанию их прежние полные ответы сохранены. Краткий статус фоновой операции показывает этап/ошибку и `result_available`; чтобы получить итоговый объект, повторить запрос без compact. Успех постановки задания или получения статуса не равен успеху самого сценария.

## Границы первой доработки

Каталог коротких маршрутов доступен через `edt_capabilities` (маршрут `quick_check`). Сохранённый профиль и существующие команды продолжают использоваться. Автоматический учёт/удаление тестовых данных и чтение структуры произвольной открытой формы 1С в эту доработку не входят.
